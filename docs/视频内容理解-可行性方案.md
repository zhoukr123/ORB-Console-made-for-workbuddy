# ORB 控制台 · 视频内容理解（原生视频输入）可行性方案

> 目标：让控制台能"看整段视频"并回答"第几秒发生了什么"，而不是靠 ORB 自己截图/抽帧再拼给模型。
> 状态：仅方案，未改任何代码。调研时间 2026-11-01。

---

## 一、先纠正一个前提：没有模型是逐帧看的

所有商业与开源视频理解通道，服务端都在做帧采样（Gemini 默认 1 fps，百炼 `fps` 默认 2）。所以"不抽帧"买不到"每一帧都看"，真正买到的是下面四件事——而这四件正好是当前抽帧方案失准的根因：

| # | 抽帧拼图法的缺陷 | 原生视频通道给到的 |
|---|---|---|
| 1 | 模型不知道帧与帧的时间间隔，只能按"然后…然后…"猜顺序；问"第几秒"必错 | 每帧带**绝对时间戳**，`fps` 参数显式告知帧间隔，答案能落到 `MM:SS` |
| 2 | 帧之间只有 2D 位置编码，无时序建模 | 交错 MRoPE 把时间维编码进注意力（Qwen3-VL），或原生音视频对齐（Gemini） |
| 3 | 音轨完全丢失，"说了什么、什么语气"无从判断 | Gemini 直接把音轨当输入（32 tok/s）；Qwen-Omni 同理 |
| 4 | 要么一次塞十来张（上下文浪费、容易漏），要么多轮（上下文断裂、费用叠加） | 一次请求吃完整段，服务端按 token 预算规划采样率 |

另一条现实理由：ORB 现在的"看屏幕"是 `screenshotRegion` + `/api/vlm` 的截图循环，对**录制文件**用同一套等于让 ORB 逐帧截播放器——既慢又不稳（播放器进度、遮挡、丢帧全都算误差）。

## 二·补、实测记录：你现在的配置就能跑（2026-11-01）

**结论：不用加任何模型。** 本机现有槽位实测：

| 槽位 | 模型 | 视频（base64） | 图片 | 说明 |
|---|---|---|---|---|
| primary | `glm-4.6v-flash` | **HTTP 429**（连图片也 429，0.5 s 即拒） | 429 | 智谱免费模型高峰限流，网关层面拒绝，与能力无关 |
| backup（思考模型） | `glm-4.1v-thinking-flash` | **HTTP 200，全部通过** | — | 内置深度思考，免费，64K 上下文 |

`glm-4.1v-thinking-flash` 的实测矩阵（问题均为"画面在第几秒变色"，真值已知）：

| 时长 | 分辨率 | 文件 | prompt_tokens | 每帧 token | 结果 |
|---|---|---|---|---|---|
| 5 s | 480×270 | 3 KB | 888 | ~296 | 200 |
| 30 s | 640×360 | 11 KB | 9 084 | 303 | 200，答 16（真值 15，**+1 s**） |
| 30 s | 640×360 | 11 KB | 9 084 | — | 200，传 `fps:2` **被忽略**，token 不变 |
| 30 s | 1280×720 | 15 MB | 35 994 | 1 200 | 200 |
| 30 s | 1920×1080 | 36 MB | 45 354 | 1 512 | 200（**36 MB 体积通过**） |
| 150 s | 480×270 | 46 KB | 44 192 | 147 | 200，答 **150**（完全正确） |
| 480 s | 480×270 | 73 KB | 45 370 | ~147 | 200，答 **240**（完全正确） |

从数据读出来的四条硬规律：

1. **帧率锁死 1 fps，不可调。** 传 `fps` / `max_frames` 都不改变 token，服务端自己决定采样。
2. **总帧数封顶约 300 帧。** 150 s → 300 帧（1 fps）；480 s 仍是 ~308 帧（间隔 1.6 s）。所以**时长 ≤5 分钟才有 1 fps 精度**，超过就均匀降采样，1 小时的片子变成 12 s 一帧——**长视频必须切片，否则时间定位会烂掉**。
3. **token ∝ 分辨率，与码率无关。** 每帧约 `像素 × 1.3e-3`（封顶 ~1500）。720p→360p 省 4 倍 token；降码率只省上传时间（15 MB 上传 24 s、36 MB 上传 32 s，这才是"要压缩"的真实理由）。
4. **思考输出是内联的**：`<think>…</think><answer><|begin_of_box|>16<|end_of_box|></answer>` 全部混在 `content` 里，另外还可能单独给 `reasoning_content`。**解析必须先剥这三类标记**，否则时间轴里会混进整段内心戏。

成本：该模型免费。若换 FlashX（2 元/百万 token），1 分钟 720p ≈ 72 k token ≈ 0.14 元。

---

**成本量级**（qwen3-vl-plus，$0.20/1M 输入、$1.60/1M 输出，2026-10 第三方价目，需以官网为准）：1 分钟 720p @1fps ≈ 60 帧 ≈ 2–7 万输入 token ≈ **¥0.03–0.1**。10 分钟录屏约 ¥0.3–1。Gemini 低分辨率档 1 分钟仅约 6 k token，更便宜。结论：**短录屏的成本可以忽略，不需要做省钱的复杂裁剪**。

## 三、落到 ORB 的三条硬约束（这决定方案长什么样）

1. **后台 Agent 读不了视频。** 附件是"引用语义"，只把路径拼进任务文本，CLI 是纯文本 agent。→ 视频理解必须由 ORB 自己完成，产出**文本索引**再喂给 Agent。这不是权宜之计，而是唯一路径。
2. **视觉密钥在主进程**（`get-vision-key`），bridge 是独立 Node 进程。现有两条绕法：`/api/vlm` 代理（面板把 baseUrl/key/model 传给 bridge 代发，绕 CORS）和 `LIVE.pendingAgent`（把活儿挂给面板）。→ 视频只能复用 `/api/vlm` 这条，但**不能把 100 MB base64 过 IPC**（字符串序列化会翻几倍内存）。必须改成 **bridge 收路径、自己读盘、自己转 base64**。
3. **`/api/vlm` 现有实现写死了 `messages`**，`video_url` 是 content 数组里的元素，可以原样透传——所以**不需要新协议**，只需新增一条 `POST /api/video`（或给 `/api/vlm` 加 `videoPath` 字段），由 bridge 拼 content。工作量主要在这里，不在协议。

## 四、推荐架构 v2：三级漏斗（吸收两个开源项目的硬约束）

> 本节是 v2 的思考过程，其中两处已被第九节的实测与文献推翻（拼图的 token 优势、拼图读内容的可靠性）。**最终方案以第九节 v3 为准。**

先推翻原方案的主路径——**"原生视频直传"不能当主力**，原因是我们自己实测出来的一条算术：

> 1080p 每帧 1512 token，原生通道封顶 ~300 帧 → 10 分钟录屏 ≈ **45 万 token**。而 `glm-4.1v-thinking-flash` 只有 **64K** 上下文。
> 换言之：**64K 上下文在 1080p 下只装得下约 43 秒**。这不是调参能解决的，是物理上限。

两条路线的账（10 分钟 1080p 录屏）：

| 路线 | token | 上下文 | 时间精度 | 小字可读 |
|---|---|---|---|---|
| 原生视频（降到 480p） | ~44 k | 勉强 | **2 s/帧**（300 帧封顶后降采样） | 差 |
| 原生视频（原分辨率） | ~450 k | **爆** | — | — |
| **关键帧总览图** | **6–12 k** | 轻松 | 由我们控制（烧时间码） | **好**（每格 380 px） |

关键帧路线省 5–50 倍，而且**恰好命中 ORB 的主场景**：录屏/教程/PPT 画面变化稀疏，10 分钟常常只有 30–60 个"真的变了"的时刻。高动态视频才轮到原生通道。

### 漏斗：越往下越贵，上一层觉得有事才下沉

```
视频文件
  │
  ├─ L0 元数据      ffprobe：时长/分辨率/帧率/音轨有无            0 token
  │
  ├─ L1 文本层      本地 ASR（复用现成 asr/）→ 带 [MM:SS] 的文字稿   0 token
  │                 ↳ 这一层就能回答"讲了什么"，且可全文检索
  │
  ├─ L2 总览层      场景差异抽帧 + 去重 + 12 格/张 + 烧时间码        1.5–3 k/张
  │                 ↳ 回答"整体流程/有哪些阶段"
  │
  └─ L3 精读层      ① 原生视频（≤2 min 窗口）  ② 单帧原图（全分辨率）
                    ↳ 只对"用户真正问的那 30 秒"下沉
```

路由表（这决定钱花在哪）：

| 用户问法 | 走哪层 |
|---|---|
| "这视频讲了什么" | L1 文字稿 + L2 总览图，**不碰原生通道** |
| "第 3 分钟那个报错是什么" | L1 文字稿定位 → L3 单帧原图（或 30 s 原生切片） |
| "这个按钮叫什么" | L2 找到格 → L3 单帧原图（总览图小字可能不够） |
| "他讲到定价策略时屏幕上是什么" | **L1 关键词反查时刻 → L3 定向补帧**，连 L2 都不用跑 |

最后那条是 `xiaohui5206/let-ai-read-video` 的"关键字定位关键帧"，也是最省的一条路：**用文本反查画面**，而不是把画面全看一遍。

### 三个必须抄对的参数（来自 `ztough926/video-understanding` 实测）

1. **每张 ≤12 格、列数 ≤4、总宽 ≤2400 px。** 原因很反直觉：视觉编码器会把整张图压到长边 1080–1568 px 再送进模型，所以**每格能分到多少像素，只取决于"这张图有几格"，跟你把图画多大几乎无关**。实测 4 分 42 秒片子：
   - 12 格 / 3 列 / 1600 px → 每格 ~380 px，小字全可读 ✅
   - 24 格 / 4 列 / 2400 px → ~270 px，正文可读、小字吃紧
   - 40 格 / 6 列 / 9600 px → ~180 px，糊；而且 9597 px **直接被读图端拒收**
2. **时间码必须烧在格子上**（`#003 00:15`），右下角或格子下方。不烧码，模型就只能说"中间某个画面"，索引失去锚点。
3. **"等它变完"再选帧。** 画面变化发生时别急着截，等动画稳定后那一帧才是完整画面；否则会抽到元素还没出现/已经消失的空白中间态。`ffmpeg` 的 `scdet` 只给切换分数，做不到这点，需要逐帧差分 + 稳定判定自己实现。

### 一个 ffmpeg 陷阱（会让实现当场翻车）

**不要**用 `select='eq(n,0)+eq(n,17)+eq(n,88)+...'` 这种表达式一次挑上百帧——表达式长度会超出 ffmpeg 解析器上限直接报错（ztough 踩过，改成 Python 侧按帧号筛、只解码一遍）。ORB 在 Node 里同理：**解一遍流，边解边按帧号决定存不存**，不要拼滤镜表达式。

### 数据流（修订后）

```
录制完成 / 选视频
   │  main.js: videoIndex(filePath, opts)        ← 新增 safeHandle
   ├─ L0 ffprobe → 决定走哪层（时长/分辨率/有无音轨/是否录制中）
   ├─ L1 asr/make_srt.py（本地 whisper）→ transcript.srt + [MM:SS]
   ├─ L2 抽帧（场景差分 + 去重 + 稳定判定）→ 拼 12 格总览图（ffmpeg tile + drawtext 烧码）
   ├─ L3 按需：≤2 min 窗口走 /api/video（base64 原生视频）
   │              或 单帧 PNG 走现有 /api/vlm（image_url）
   ↓
   cache/vidx/<sha1(path+mtime)>/{report.md, manifest.json, sheets/*.jpg, frames/*.jpg}
   ↓
   面板把 report.md 路径拼进任务文本（复用现有附件机制）→ 后台 Agent 读取并回答
```

**为什么落"索引"而不是一段摘要**：一次理解有成本也有延迟。落成带时间轴的 markdown + 图片目录，用户追问时 Agent 直接读文件、按需补看单帧，**不重复付费**；同一份索引还能被后续任意任务复用。

索引结构（人机双读）：

```json
{
  "duration": 612.4, "w": 2560, "h": 1440, "fps": 30,
  "sheets": [{"path": "sheets/s01.jpg", "cells": 12, "t0": 0, "t1": 137}],
  "keyframes": [{"n": 3, "t": 15.0, "path": "frames/kf_003_15s.jpg", "diff": 0.061}],
  "events": [{"t0": 12.0, "t1": 19.5, "what": "打开设置 › 录屏页", "conf": 0.9}],
  "texts":  [{"t": 33.2, "text": "保存成功", "where": "toast 右上"}],
  "speech": [{"t0": 40.0, "t1": 44.2, "text": "这里应该先点应用", "src": "asr"}]
}
```

渲染成 md 时按 `MM:SS` 升序成表，每个事件后面挂"该时刻关键帧"的相对路径，末行附"可疑/未确定"清单。

**为什么产出"索引"而不是直接给一段摘要**：一次视频理解调用是花钱的、也是慢的（10 min 视频约 20–60 s）。落盘成带时间轴的 markdown，用户追问"第 3 分钟那个报错是什么"时 Agent 直接读文件，**不再重复付费**；索引还能被后续任意任务复用。


索引结构（同时给人读和给机器读）：

## 五、入口放在哪（交付的一部分）

- **设置 › 视觉模型**（现有 `data-pane="vision"` 页签）：在主力/备选槽位下加一行能力标记"支持视频"，按实测结论给 `glm-4.6v-flash` / `glm-4.1v-thinking-flash` 打 `video: true`。**不做新的 Provider 体系**，复用 `VISION_PRESETS` + `makeSlot`。
- **设置 › 录屏与截屏**：加"录制结束后自动生成内容索引"拨杆（默认关）。
- **对话框加号菜单**：`video` 类附件（`panel.html:6282` 已有 `['mp4','mov','webm']` 分类）追加一项"理解这段视频"——触发后按 L0 自动选层级，用户不必懂漏斗。
- 路由 chip 不加新族：视频理解属于「视觉」族（`data-route="vision"`），在 `Ctrl+K` 的「功能」族下挂一条"视频索引"。

## 六、必须防的坑（都是这个项目踩过的类型）

1. **L3 的 base64 内存**：只有精读层才传原生视频，单段被 ≤2 min 限制住。但仍要 >40 MB 先压：100 MB 文件 → 133 MB base64 → `JSON.stringify` 再复制一份，进程峰值 ≈ 400 MB。总览层走 `image_url`（单张 <1 MB），没有这个问题。
2. **录制未落盘**：录制中文件的 `moov` 还没写，读出来是坏文件。必须先过 `mp4finalize.js`，或在入口处判断"是否正在录制"直接拒。
3. **时长/体积超限的静默失败**：百炼超限报 `InvalidParameter` 之类，不能只 catch 记日志，必须回明确文案（"视频 78 分钟，超过单次 1 小时上限，将分 16 段处理，预计 ¥0.8"）。
4. **ffmpeg 不是必然存在**：本机有（winget 9.0.2），但发布版不能假定。探测失败就退回"只接受 <75 MB 且 <1 h 的视频，否则提示安装"，不要静默失败。
5. **密钥路径**：沿用"Key 只在主进程、明文不下发"口径。`/api/video` 接受主进程传入的解密后 key（进程内一次性使用，不落盘、不写日志、不进审计明文）。
6. **隐私**：视频会离开本机。面板必须在按钮旁一行明示，并提供"仅本地（llama.cpp）"档位。
7. **计费可见**：现有 `TOK` 账本只记 CLI 与台词两笔，视频调用要并入同一本账，否则又是一笔"看不见的支出"。调用前按 `时长 × fps × 每帧 token` 给预估值。
8. **429 要重试不要降级到抽帧**：主力 `glm-4.6v-flash` 实测高峰期连图片都 429，必须把 429 当"换槽位重试"信号（现有 primary→backup 机制正好），而不是当成"模型不会看视频"。
9. **`max_tokens` 必须给足**：思考模型默认会把 1024 预算全用在 `<think>` 上，答案被 `finish_reason: length` 截断，表现为"索引只有半句话"。
10. **抽帧差异只算全局平均会漏**：角落一个小图标在动，会被大片静止像素稀释到 0.004（与噪声同级），判定不出变化。必须同时算 8×8 分块里"最剧烈那一块"的差异再取较大值——同一场景能拿到 0.06，区分度才干净。
11. **别用 `select` 表达式挑上百帧**：表达式会超出 ffmpeg 解析器上限直接报错。解一遍流、按帧号决定存不存。
12. **场景检测 ≠ 内容识别**：`scdet` 只告诉你"这里切换了"，不知道切到了什么。所有语义结论必须来自 L2/L3 的模型调用，不能拿 `scdet` 分数冒充"检测到事件"。

## 七、工作量与里程碑

| 阶段 | 内容 | 复杂度 | 备注 |
|---|---|---|---|
| M1 | **L1 文本索引**：ASR → `[MM:SS]` 段落 + 关键词检索（复用 `asr/`） | 低 | **地基**。做完就能零成本回答"讲了什么"，且不做这层后面全是错的 |
| M2 | **L3 证据帧**：命中窗口抽 6–8 帧 → `/api/vlm`（4096 tokens + 剥 `<think>`） | 中 | "第几秒那个按钮叫什么"靠这层，分开传不拼图 |
| M3 | **L2 导航**：场景切段 + 每段代表帧（拼图可选） | 中 | 只在"问题无法用文字表达"时才启用 |
| M4 | **L4 原生切片** ≤2 min（已实测可跑，需 `primary→backup` 回落） | 低 | 只在连续动作/时序因果时用 |
| M5 | 入口（设置 › 视觉 / 加号菜单 / 录屏后自动索引）+ 落盘缓存 + TOK 记账 | 中 | 功能放哪个页签是交付的一部分 |

**验收基准**：拿 `video-pilot/` 的现成 mp4 与本次调研的 5 分钟/8 分钟样片，提问"第 X 秒发生了什么"，时间戳误差 ≤2 s；同一文件二次提问不产生新调用；**单次追问的图片数 ≤8 张、总 token ≤10 k**（超过说明没按 query 定位，退回了"全片铺开"）。

## 九、v3 修订：外部研究推翻了两处设计

我又扩了一圈文献（2026 年 CVPR/ICML/ACM MM 与生产实践），加上一次实测，**上一节的三级漏斗有两处要改**。

### 推翻 1：「拼图省 token」被高估了（实测）

同一段 30 秒视频，12 帧，问"逐格说出颜色"：

| 输入方式 | prompt_tokens | 耗时 |
|---|---|---|
| 1 张 12 格拼图（1607×1212） | **2 481** | 5.0 s |
| 12 张单帧（640×360） | **3 640** | 7.0 s |

拼图只省 **32%**，不是我上一轮估的 5–50 倍。图的 token 是按整图像素算的，拼起来并不打折。真正的差别在分辨率：

- 单帧 640×360（~300 tok/帧）：拼图省 32%
- 单帧 1280×720（~1 200 tok/帧）：拼图省 **83%**（2 481 vs 14 400）

也就是说，拼图是**用清晰度换 token**，不是凭空省。而 ztough 自己在 README 里就承认了代价："每格只剩一两百像素，字幕全糊"。

### 推翻 2：拼图本身有系统性精度缺陷（论文证据）

- **MMLongCite-HR**（arXiv 2510.13276）把图片网格化后，citation F1 全面下降：Qwen2.5-VL-7B 25.69 → 15.19，Gemini-3-Pro 84.68 → 63.78。原因写得很明确：**拼接把一张大图序列化成 1D，同一子图内相邻 patch 在 token 序列里被推得很远，破坏空间邻接**，注意力难以重建局部语义。
- **MIOH**（CVPR 2026）多图同时分析 vs 单图分开分析，29 个模型**无一例外下降**：Gemini-2.5-Pro 90.0 vs 95.8、Qwen2.5-VL-7B 85.0 vs 93.5、GPT-5 78.0 vs 93.5。结论是"跨图整合"本身在放大幻觉，不是误差累积。
- **LOCOVQA** 图像从 1 张加到 36 张，多数模型准确率掉 **50%+**，且拼图与分开传**两种设置都掉** → 不是降采样的锅，是注意力的硬限制。
- **MultipanelVQA**：GPT-4o 单图强，排成网格就暴跌（"content interference"）；训练在 3×3 的模型遇到 4×4 直接失败。

**所以拼图只能用来"导航"，不能用来"读内容"。** 读证据必须回单帧原图，且单次不超过 8–12 张。

### 推翻 3：「全片均匀取帧」不如「按 query 定位」

- **ProVCA**（2026-04）：三段渐进压缩（段定位 → 片段选择 → 关键帧精化），**每个视频只用 4.2–7.3 帧**，NExT-QA 80.5%，比全片建树的 VideoTree 高 4.9%。
- **T³**（2026）：递归时间聚类建**问题无关的时间树**（每节点一个代表帧），推理时 answer→retrieve→explore 循环，证据不足才展开分支。同帧预算下 Qwen2.5-VL-7B 在 LongVideoBench +4.6%、LVBench +4.4%。
- **HiMu**（2026-03）：一次纯文本 LLM 调用把 query 拆成逻辑树，路由到 CLIP/OCR/ASR/CLAP 各轻量专家，16 帧就超过用 32–512 帧的 agent 系统，FLOPs 只有 1/10。

共同结论：**先按问题定位，再精读。全片铺开是最差的选择。**

### v3 架构：文本先行 + 按需取帧

```
L0 探底     ffprobe 时长/分辨率/有无音轨                    0 token
L1 文本索引  本地 ASR → [MM:SS] 段落            ← 主索引，0 token
            OCR（屏幕文字）可选，也进同一时间轴
L2 视觉导航  仅当问题无法用文字表达时才用（"界面长什么样"）
            拼图只做"哪一段值得看"的判断，不下结论
L3 证据帧    命中窗口内抽 6–8 张【单帧原图】，分开传，不拼
L4 原生视频  只给"连续动作/时序因果"这类问题，≤2 min 切片
```

关键变化：**L1 从"辅助"升为主索引。** 因为文字检索是 0 成本、毫秒级、可全文匹配的，而视觉定位要花 token 还容易漏。用户问"他讲定价策略时屏幕上是啥"——先在文字稿里命中 `[12:30–13:10]`，只对这一小段抽 6 帧，成本是 6 × 300 = 1.8 k token，比看全片准得多也便宜得多。

### 五条工程原则（来自生产实践，可直接落地）

1. **检索时融合，不要索引时融合。** 视觉、语音、OCR 各自存成独立记录，共享 `videoId + 时间戳`，查询时按时间窗合并。跨模态"同时命中"是最强的相关性信号；索引时揉成一个混合表示反而把它丢掉了。
2. **语义分块，不要固定间隔切。** 按场景/话题边界切（TwelveLabs 的做法），而不是每 30 秒一刀。
3. **昂贵解释只做一次。** 入库时算好，产物供后续任意次复用——这就是"落索引"的工业版说法。
4. **索引时做问题无关的层级，查询时按需展开。** 别为每个问题重看全片。
5. **能力边界要诚实**：这些项目都明说"音频不在覆盖范围内"。ORB 也一样，看画面和听声音必须分开标来源，不能拿画面猜台词。

### ORB 的落地取舍：抄什么、不抄什么

| 外部方案 | ORB 是否采纳 | 理由 |
|---|---|---|
| 层次时间树（T³ / ProVCA） | **采纳轻量版**：场景边界切段 + 每段一个代表帧 | 不需要训练，纯 ffmpeg + 差分即可 |
| 按 query 定位再精读 | **采纳** | 这是成本与精度的最优解，且实现简单 |
| 文字先行（ASR 主索引） | **采纳** | 你已有 `asr/`，0 成本 |
| 检索时多模态融合 | **采纳轻量版**：按时间窗对齐，不上向量库 | 单机单用户不需要向量检索 |
| 单帧证据 / ≤8 张分批 | **采纳** | 论文证据充分 |
| 拼图做导航 | **仅在必要时用**，且只下"哪段值得看"的判断 | 精度不足以读内容 |
| 向量库 + CLIP 嵌入 | **不采纳** | 单机场景过度设计，增量依赖大 |
| caption-then-index（每秒一次 VLM 描述） | **不采纳** | 成本爆炸，ORB 是按需而非建库 |
| 托管 API（TwelveLabs 等） | **不采纳** | 数据出境的代价与"本地优先"冲突 |
| 视觉 token 压缩（FastV/FrameFusion 等） | **不采纳** | 需要改模型内部，API 场景拿不到 |

**修订后的成本量级**（10 分钟 1080p 录屏，回答"讲了什么"）：

| 层次 | 调用 | token |
|---|---|---|
| L1 ASR | 本地 whisper | 0 |
| L2 导航（可选） | 1 张拼图 × 4 段 | ~10 k |
| L3 证据（按需） | 用户追问时 6–8 帧 | ~7–10 k/次 |

对比 v2 的"全片 12 格总览"（6–12 k，但读不了细节）：**v3 的每次追问更贵一点，但答得准，且不用为没问到的部分付费**。



## 十、v4：社区还有四条路线，其中一条只有 ORB 能做

第九节的文献是学术口径（怎么用最少帧答对题）。这一轮看的是**开源社区怎么落地**，结果发现四条和"抽帧→拼图"完全不同的路线。

### 四条路线

| 项目 | 路线 | 核心做法 |
|---|---|---|
| **ScreenPipe**（18.8k★, YC S26, MIT） | 屏幕记忆 | **UIA 树优先、OCR 兜底**；事件驱动捕获；SQLite+FTS5 全文检索 |
| **微软 Skill Recorder**（MIT, 2026） | 录屏→技能 | 录一遍操作 → 生成 `SKILL.md`，**输出优先用 agent 原生工具，不回放 UI 点击** |
| **ZASSHA / AI-DocGen / AutoDocs** | 录屏→文档 | 相似度阈值 + 最小间隔做步骤检测 → 逐步骤配图描述 → PDF/PPT/Word |
| **Stream-Clipper-Factory** | 借外部信号定位 | 弹幕密度 + 情绪词 + 语义重合（ASR×弹幕 Jaccard）三信号加权 → 高斯平滑 → 峰值检测 |
| **MomentSearch**（Apache-2.0） | 双路检索 | 视觉帧 + 转写两路分开检索，返回带 keyframe/时间戳的**「seen / said」标签**；两路都不过阈值就**不调 LLM** |

### 精华 1：UIA 树优先，像素是兜底（ScreenPipe）

它没把屏幕当图片：**先扒操作系统自己的无障碍树**（按钮名、角色、状态、坐标），拿不到才 OCR。代价差异是硬数据：**CPU 5–10%，而纯 OCR 方案 20–30%+**。存储也一样靠"事件驱动"（切窗、点击、打字停顿、滚动才采）压到 **8 小时 300 MB**，连续抽帧要 2 GB。

社区在 computer-use 上已经形成共识，顺序是固定的：

```
① UIA / AT-SPI 树   → 几百 token，点击精确，能读状态（禁用/选中/聚焦）
② OCR               → 树里没标签时用
③ 截图 + 视觉模型    → 只有画布、游戏、远程桌面这类"只有像素"的才用
```

成本差多少：一张 1092×1092 截图约 **1 600 token**，而一个窗口 40 个控件的树列表**几百 token**。而且截图在 20 步任务里会累积进上下文，树不会（它是文本，可缓存）。

**但这条对 ORB 的真正价值不是"操控"，而是"录制时的旁白"。**

### 精华 2：这条路只有 ORB 这种工具能走

关键分叉：**视频有两种来源，而它们的信息量根本不同。**

```
① ORB 自己录的     录制时就能同步采 UIA 树 / 窗口标题 / 焦点 / 点击位置
                   → 视频自带一份「结构化字幕」，几乎零 token，比任何视觉模型都准
② 外部给的视频     只有像素，UIA 早就消失了，只能走 v3 的抽帧+证据帧
```

ScreenPipe 只能做①（它一直在录），阅影/bili-vision 只能做②（它们拿到的是成品视频）。**ORB 两边都能做**，因为它就是那个录屏的人——这是本次调研里唯一一条别人抢不走的优势。

具体到实现：录制时按事件（点击/切窗/输入停顿）写一条 JSONL：`{t, win, ctrl, role, value, click:{x,y}}`。事后这份日志就是"第 12 秒点的是『保存』按钮"的**事实**，不需要模型猜。

### 精华 3：事件驱动，不要固定帧率

ScreenPipe 的 300 MB / 8 h 不是压缩出来的，是**不采没变化的帧**。我们 v2 的方案是 `fps=0.4` 均匀抽，等于把 90% 的预算花在静止画面上。改成三路触发：

- 画面变化（差分超阈值）
- **用户操作**（点击/键盘/切窗 —— ORB 本来就有全局钩子能力）
- 场景切换（`scdet`）

### 精华 4：输出 SKILL.md，而不是"总结"

微软 Skill Recorder 的设计哲学值得抄一句话：

> **Output prefers the agent's native tools over replaying UI clicks, so one example can generalize to many cases.**

它把"录一遍操作"变成**可复用的技能包**，而不是一段像素回放。对 ORB 的启发：录屏分析的终点不该是"这段视频讲了什么"，而是**"这套操作能不能被复用"**。产出 `SKILL.md` / 操作手册的价值比摘要高一档，而且它天然是文本。

### 精华 5：两条防浪费的闸

- **seen / said 标签**（MomentSearch）：每条证据标明"看到的"还是"听到的"。这正好治我们前面提到的病——不能拿画面猜台词。
- **confidence gate**：两路检索都不过阈值就**不发起 LLM 调用**，直接回"没找到"。省掉大量"硬答"。

### 精华 6：用外部信号给时间轴加权（Stream-Clipper）

它用弹幕密度 + 情绪词命中 + 主播话与弹幕语义重合，三路加权再高斯平滑找峰值。ORB 没有弹幕，但有等价物：

| Stream-Clipper 的信号 | ORB 的等价物 |
|---|---|
| 弹幕密度 | **鼠标点击/键盘输入密度**（用户忙 = 有事发生） |
| 情绪词频率 | 麦克风能量/语速突增（强调） |
| 语义重合 | ASR 关键词与画面 OCR 文字重合 |

### v4 架构：按来源分叉

```
                    ┌─ ① ORB 自己录的 ─────────────────────────┐
                    │  L0 ffprobe + 录制期间的事件 JSONL        │
                    │     （点击/切窗/焦点/UIA 片段，0 token）   │
                    │  L1 UIA 时间轴 + ASR 文字稿  ← 主索引      │
                    │  L2 仅补 UIA 覆盖不到的区域（画布/远程）    │
                    │  L3 证据帧（单帧，≤8 张）                  │
                    │  → 产出 report.md + SKILL.md（可复用技能） │
                    └──────────────────────────────────────────┘
                    ┌─ ② 外部视频 ─────────────────────────────┐
                    │  L0 ffprobe                              │
                    │  L1 ASR 文字稿（主索引）                   │
                    │  L2 拼图导航（只在问题无法文字表达时）      │
                    │  L3 证据帧（单帧原图，≤8 张）              │
                    │  L4 原生切片（≤2 min，连续动作）           │
                    └──────────────────────────────────────────┘
```

两条通道共享同一个产出格式（`report.md` + `manifest.json`），只是①多一份事件时间轴、且**大半问题根本不用调模型**。

### 对第九节取舍表的补充

| 社区方案 | ORB 是否采纳 | 理由 |
|---|---|---|
| UIA 树优先、OCR 兜底 | **强烈采纳（仅①通道）** | 录制时机稍纵即逝，事后补不回来 |
| 事件驱动采样（点击/切窗触发） | **采纳** | 比固定 fps 省一个量级，且更贴"有事发生" |
| 产出 SKILL.md / 操作手册 | **采纳** | 比摘要高一档，且天然是文本 |
| seen/said 标签 + confidence gate | **采纳** | 防幻觉 + 防白花钱，实现成本极低 |
| 三信号加权定位 | **采纳轻量版**：点击密度 + 画面变化 | 不需要弹幕 |
| SQLite + FTS5 全文检索 | **可选** | 单机用 JSONL + 现成检索即可，量大再上 |
| 三层确定性权限（per-pipe 令牌） | **不采纳** | ORB 是单用户单机 |
| 云端同步 / 订阅版 | **不采纳** | 与本地优先冲突 |

## 十一、输入解析：本地文件 + 视频链接（2026-11-01 实测，全部跑通）

这一节回答「能不能让用户直接丢一个链接或一个文件，控制台自己解析」。答案是能，而且**不需要装 yt-dlp、不需要装 ffmpeg、不需要合并音视频**——三条常见的"以为必须"都不成立。

### 11.1 先纠正两个前提（本轮实测推翻的）

**纠正 A：工程里根本没有 ffmpeg，但 `asr/venv` 里有一整套。**

```
$ grep -rn "ffmpeg|ffprobe" orb/            → 0 条
$ ls asr/venv/Lib/site-packages/av.libs/
  avcodec-62  avformat-62  avfilter-11  avutil-60  ...（全套 FFmpeg 共享库）
$ ls asr/venv/Lib/site-packages | grep ^av   → av 18.1.0（PyAV）
```

`asr/requirements.txt` 的注释自己就写了：「含 av → FFmpeg 解码库」。也就是说：**探底、解码、抽帧三件事，用已有的 PyAV 就能做，不必打包 `ffmpeg.exe`（省 ~100MB）**。代价是这套能力绑在"用户装了本地离线识别"这个可选依赖上（见 11.9 第 3 条）。

**纠正 B：ORB 现在录出来的视频没有音轨——ASR 通道对自录视频不成立。**

```
$ grep -rln "wasapi|AUDCLNT|loopback" orb/native/src/   → 0 条
$ grep -n "audio:" orb/desktop/panel.html
  7531:      audio: false,
$ python -c "av.open('tmp/_v8min.mp4')"  → streams = [('video','h264')]   ← 只有视频流
```

原生录制（`orb-cap.c`，Desktop Duplication）和渲染层录制（`MediaRecorder`，`audio:false`）**都不采集音频**。所以第十节 v4 架构里「①自录的 → ASR 文字稿」这一支**当前无法落地**，必须先补音轨（11.9 第 6 条给了三条路径）。这不是解析层的问题，是录制层的历史欠账，但会直接卡住自录通道。

### 11.2 入口一：本地文件——复用附件通道，只加一层"这是视频"的分支

现成的（`main.js`）：

| 位置 | 现在做什么 |
|---|---|
| `:2485 pickAttachments()` | 文件对话框，filters 已含 `mp4 / mov / webm` |
| `:2481 ATTACH_MAX_SIZE` | 单文件 100 MB 上限，超限进 `skipped` |
| `:5510 safeHandle("attach-pick")` | 渲染层拿到的只是 `{name, path, size}` |
| `:2476` 注释 | **引用语义，不拷贝**——路径拼进任务文本，后台 Agent 凭路径读 |

问题在于最后一行：**后台 Agent 拿到路径也读不了视频**（CLI 侧没有解码器）。所以视频文件不能走"引用"语义，必须走"预处理"语义。

改动很小：`pickAttachments()` 返回前给每个文件加一个 `kind` 字段（`image / video / audio / other`），视频的走新分支 `videoIngest(path)`，其余保持原样。渲染层据此决定是渲染缩略图芯片还是视频芯片（显示时长、有无音轨、就绪状态）。

三道校验（缺一个就会出难查的错）：

1. **录制中拒收**。正在录的那个文件 moov 还没写（`mp4finalize` 未收尾），PyAV 会 open 成功但 duration 为 0、decode 报错。判据：录制态或文件在 `recordings/.tmp/` 下 → 直接提示"这段还在录，停了再给"。
2. **路径含中文**。主进程 spawn Python 时不要过 `cmd`（GBK 会吞），直接 `spawn(py, [script, path])`；脚本内 `path` 用宽字符接，读文件时显式 `encoding="utf-8"`。本项目已有同类事故（`.ps1` 必须纯 ASCII）。
3. **超限要分开报**。现有 `skipped`（超限）/ `failed`（读不到）分离的设计要保留——视频场景下"超过 100MB"和"文件被移走"必须给不同文案。

### 11.3 入口二：网络链接——B 站匿名直链已实测跑通，不需要 yt-dlp

本机 `which yt-dlp` 为空。但不影响：B 站的取流链路是纯 HTTP，两步就够。

```
① 归一化（三种输入都收敛到 bvid）
   https://b23.tv/BV1P73G6zENo        --302--> https://www.bilibili.com/video/BV1P73G6zENo
   https://www.bilibili.com/video/BV1P73G6zENo?p=2&vd_source=...
   av123456                            → aid
   正则抽出 (BV[0-9A-Za-z]{10}) 或 av(\d+)；短链跟随一次 302 即可

② 元信息
   GET https://api.bilibili.com/x/web-interface/view?bvid=BV1P73G6zENo
   → data.pages[] 每项含 cid / part（分 P 标题）/ duration
   → data.title, data.owner.name, data.duration

③ 取流（每个分 P 单独取）
   GET https://api.bilibili.com/x/player/playurl?bvid=<>&cid=<>&qn=64&fnval=16&fourk=1
   → data.dash.video[] / data.dash.audio[]，各自带 baseUrl + bandwidth + codecs
```

实测返回（`BV1P73G6zENo`）：

```
code=0 msg=OK
video: id=32 avc1.64001F bw=156241 768x480
       id=16 avc1.64001E bw= 92265 576x360
audio: id=30232 mp4a.40.2 bw=80396
       id=30216 mp4a.40.2 bw=65572
duration = 631
```

四条必须知道的实测事实：

- **匿名只给 480p**。请求写 `qn=64`（720p）但返回被降级到 `id=32 / 768×480`。要 1080p 得带登录 Cookie（`session.defaultSession.cookies` 里捞 `SESSDATA`）。对"理解内容"够用，对"读屏幕小字"不够（见 11.9 第 2 条）。
- **必须带 `Referer: https://www.bilibili.com`**，否则 CDN 直接 403。Electron 里用 `net.request` 设 `req.setHeader('Referer', ...)`。
- **直链有 `deadline` 参数，约 2 小时**。实测取到 `deadline=1793555007` → `2026-11-02 01:43`，距取流时刻 1.9 小时。**所以只缓存已落盘的文件，永不缓存 URL**。
- **`fnval=16` 返回 DASH（音视频分离）**。这是很多人以为"必须 ffmpeg 合并"的来源——见 11.4，其实不必合并。

下载实现（主进程新写，工程里目前没有任何流式下载）：

```js
// ❌ 不要 fetch + arrayBuffer：12MB 尚可，1 小时 1080p 会把内存顶穿
// ✅ net.request 流式写盘，且天然走 Chromium 的代理/证书栈
const req = net.request({ url, redirect: "follow" });
req.setHeader("Referer", "https://www.bilibili.com");
req.setHeader("User-Agent", UA);
req.on("response", (res) => {
  const ws = fs.createWriteStream(tmpPath);
  res.on("data", (c) => ws.write(c));
  res.on("end", () => ws.end(...));
});
req.end();
```

### 11.4 实测：DASH 分片能直接解开，**不需要合并音视频**

这是本轮最有价值的结论——原方案里最大的一块工程量（下载 ffmpeg、remux 音视频、处理时间戳对齐）直接消失了。

```
$ 下载 audio 直链 → 6,337,276 B (4.53s)      → _bili_a_full.m4s
$ 下载 video 直链 → 12,315,094 B (1.57s)     → _bili_v_full.m4s

$ python -c "av.open(...)"
_bili_a_full.m4s  dur=630.44s  fmt=mov,mp4,m4a  audio aac 44100Hz 2ch
                   decode → 27151 帧 = 630.44s（wall 0.28s）
_bili_v_full.m4s  dur=630.48s  fmt=mov,mp4,m4a  video h264 768x480
                   decode → 14918 帧 = 630.48s（wall 4.94s）
```

`av.open()` 一次成功、duration 与实际一致（631s）、音视频两路各自完整解码。**B 站的 `.m4s` 自带 moov，是合法可解容器，不是需要 init segment 拼装的裸分片**。

> 附带发现：截断文件（只下前 1.5MB）也能 `av.open()` 且 duration 正确，但 decode 到最后一个残包时抛 `InvalidDataError [Errno 1094995529]`。这正好可以当**下载完整性校验**用：能 open 不代表下完了，要拿 duration 和实际解出的秒数对账。

### 11.5 实测：`.m4s` 直喂 faster-whisper，不用转码不用改后缀

```
$ python tmp/_probe_asr_m4s.py      （small / int8 / CPU）
load model 2.4s
transcribe 126.4s   lang=zh  dur=630.4s  segs=186

  [   0.8 →    4.5] 这是一个可以让你的AI尊重读懂视频的项目
  [   4.5 →    8.1] 它不同于很多外国的github开源项目
  [   8.1 →   12.6] 是通过一些外部的API或者是云平台等等

  [ 626.0 →  628.4] 所以说希望能帮到大家吧
  [ 628.7 →  629.2] 谢谢
```

三个可用结论：

- **后缀无关**。`asr_server.py:377` 那段按后缀分派（`.wav/.mp4/.webm`）只是给临时文件起名，faster-whisper 内部靠 av 嗅探内容。`.m4s` 直接传进去照样能转。
- **性能基线**：small/int8/CPU = **0.2× 实时**（126.4s 转 630.4s 音频）。10 分钟片子等 2 分钟，1 小时片子等 12 分钟。这个必须做成后台任务 + 进度，不能同步等。
- **产出就是索引**：186 段带时间戳中文稿，直接就是第十节 v4 架构里那个"L1 文字稿主索引"。

### 11.6 实测：抽帧——**顺序扫一遍比随机 seek 快 6 倍**（反直觉，但数据很硬）

| 方式 | 帧数 | 总耗时 |
|---|---|---|
| 随机 `seek` 逐点取帧（0/60/300/600/628s） | 5 | **9.5s**（15 + 355 + 1768 + 3585 + 3785 ms） |
| 单遍顺序解码，每 5 秒留一帧 | 127 | **4.75s** |
| 单遍顺序解码，每 30 秒留一帧 | 22 | **4.02s** |

原因：`seek` 每次都要重建解码器、从最近关键帧一路追到目标位置；而顺序解码是流式 IO，**解码成本是固定的，编码几乎免费**（127 帧 vs 22 帧，差 0.7s ≈ 7ms/帧）。

**所以管道里不要写"按时间 seek 抽帧"**，要写"一遍扫到底，边扫边按时间戳决定留不留"。用户问某个时刻，从已落盘的索引帧里取，不再碰解码器。

`seek` 精度本身是够的（≤0.03s），但只在"真的必须补一个扫描时漏掉的点"时才用。用它有四个坑：

1. **`container.seek()` 的 offset 单位是微秒**（`av.time_base == 1000000`），**不是** `stream.time_base`。用错单位不报错，静默落回第 0 帧——我第一版就踩了，`t=60` 拿到的 pts 是 0.00。
2. **seek 后必须先丢帧**，直到 `frame.time >= t`。h264 有 B 帧重排，落点之前的旧帧会先被吐出来。
3. **mjpeg 编码上下文不能复用**。同一个 `CodecContext` 连续 encode 会在第二帧起抛 `ArgumentError: avcodec_send_frame() returned 22`（EINVAL）。每帧重建（成本 7ms，可忽略）。
4. **venv 里没有 Pillow**，`frame.to_image()` 直接 `ModuleNotFoundError`。别指望存 PNG——直接出 JPEG 字节，反正下一步就是要 base64 喂模型：

```python
vf = frame.reformat(width=640, height=400, format="yuvj420p")
cc = av.CodecContext.create("mjpeg", "w")   # 每帧新建
cc.width, cc.height, cc.pix_fmt = 640, 400, "yuvj420p"
jpeg = b"".join(bytes(p) for p in cc.encode(vf))
```

实测 640×400 JPEG 平均 **45–48 KB**（≈ 60 KB base64）。按第九节实测的 token 口径（640×360 单帧 ≈ 303 token），**一帧约 330 token，22 帧索引 ≈ 7200 token**——正好是"能铺全片又不太贵"的甜点。

### 11.7 管道：一次扫描，两级缓存

```
用户给的东西（路径 / 链接 / 粘贴的分享文本）
        │
        ├─ 路径  → 校验（录制中？超限？存在？）
        └─ 链接  → 归一化 bvid+page → view 取 cid → playurl 取 DASH 直链
                   → net.request 流式落盘（只存文件，不存 URL）
        │
   [探底]  PyAV 一次 open：时长 / 分辨率 / 帧率 / 有无音轨 / 编码     < 50ms
        │
        ├─[音轨]→ faster-whisper（后台任务，0.2× 实时）→ segments.json {t,e,text}
        │
        └─[视频]→ 单遍顺序解码，自适应间隔留索引帧（320px 小图）→ frames/f0000.jpg ...
        │
   [索引]  segments.json + 索引帧时间轴 → text.md（纯文本，0 token，可直接给 Agent 读）
        │
   [回答]  ① 文本能答 → 直接答，不看图
          ② 需要看画面 → 从磁盘取索引帧（不 seek，不再解码）
          ③ 连续动作 / 界面操作 → 原生切片，≤2 min，走已有视觉槽位（实测 200 OK）
```

间隔的取法（一次扫描所以必须一开始就定）：`step = clamp(duration / 40, 3, 30)` 秒。10 分钟片子约 15s 一帧（40 帧 ≈ 1.3 万 token），1 小时片子 30s 一帧（120 帧，太贵 → 上限 40 帧，改 90s）。

### 11.8 存储与去重

```
<userData>/cache/vidx/
  <cacheKey>/
    meta.json        {src, kind, bvid, page, duration, w, h, fps, hasAudio, createdAt}
    media/           a.m4s / v.m4s（B 站）或 symlink 记录（本地文件不拷贝）
    segments.json    ASR 产出
    frames/          f0000.jpg（索引帧）
    text.md          人类可读的时间轴文字稿（也可直接喂 Agent）
```

`cacheKey`：
- B 站：`bili_<bvid>_p<page>`——**分 P 必须独立**（一个 BV 下多集内容完全不同，混用会答错集）
- 本地：`<sha1(realpath | mtime | size)>`——用 mtime 而非内容哈希，避免每次算哈希读整个 100MB

清理：LRU，默认上限 4 GB，超了按 `meta.json.createdAt` 淘汰整个 key 目录。本地文件那条只存索引不存媒体，几乎不占空间。

### 11.9 六个必须处理的边界

1. **直链 2 小时过期** → URL 永不入库，`meta.json` 只记 `bvid/page`，需要重下时重新走 playurl。别把 baseUrl 存下来当缓存。
2. **匿名 480p 会糊** → 读屏幕文字（IDE、报错、表格）这类需求，480p 撑不住。两条路：带 Cookie 提画质（复用 `session.defaultSession.cookies`，用户在应用内登录过 B 站即可），或明确降级成"只做语义、不做精确读字"，别让模型对着糊图硬猜。
3. **没装 asr venv = 这条链全废** → 探底/抽帧/ASR 都依赖 PyAV。降级路径只有一条：把路径/URL 拼进任务文本，交给后台 Agent 自己想办法（现状）。UI 上必须在视频芯片上直说"需要先安装本地离线识别"，不能静默失败。
4. **中文路径** → 主进程 `spawn` 不过 shell；Python 侧读文件显式 `encoding="utf-8"`；`.ps1` 严禁中文（本项目已有事故）。
5. **100MB 上限与长视频冲突** → 630s@480p 是 12MB 没问题，但 1080p 1 小时会到 500MB+。本地文件这条路要么放宽上限（改成按"预估解码耗时"拒收），要么在探底后按需只取前 N 分钟。
6. **自录视频没音轨（本轮新发现）** → 三条补法，按性价比排：
   - **a. 换 API 拿系统环回音频**。注意现在用的是老式约束（`panel.html:7530`）：`getUserMedia({ audio:false, video:{ mandatory:{ chromeMediaSource:'desktop', chromeMediaSourceId } } })`。**这套写法拿不到系统音频**（只有在 `audio.mandatory.chromeMediaSource='desktop'` 这种更老的写法里才勉强可用，且极不可靠）。要拿到必须换成新 API 二件套：
     ```js
     // 主进程（Electron 44 支持，需在 app ready 后、窗口创建前注册）
     session.defaultSession.setDisplayMediaRequestHandler((req, cb) => {
       cb({ video: source, audio: "loopback" });   // loopback = 系统声音
     });
     // 渲染层
     const stream = await navigator.mediaDevices.getDisplayMedia({ video: true, audio: true });
     ```
     而且**要同时混麦克风**得再开一路 `getUserMedia({audio:true})`，用 `AudioContext` 混成一条轨——否则录不进用户自己的讲解。改动集中在渲染层 + 一处主进程注册，但会牵动现有录制链路（`cropVideo` / `captureStream` / 区域裁剪那段），不是纯增量。
   - **b. `orb-cap.c` 加 WASAPI loopback + 麦克风混音**，写进同一个 mp4 的第二条流。最正确（原生通道也受益），但是 C 层工作量，且要处理设备热插拔与采样率对齐。
   - **c. 不补，接受自录无音轨**——自录场景下 UIA 事件 + 屏幕文字本来就比听声音强（见第十节"精华 2"），语音只在"用户自己讲解教程"时才是关键信息。**建议先走 c，把 a 排进 M2。**

## 十二、Web 操作：让 AI 用你已登录的网站（2026-11-01 实测）

起因是腾讯开源的 **BrowserSkill**（`Tencent/BrowserSkill`，MIT，8k★）：让 AI 直接借用你已登录的 Chrome/Edge，不传 Cookie、不传密码。这一节回答三件事：ORB 能不能照做、社区还有哪些路线、以及上一轮说"不用装"的东西到底还剩什么用。

### 12.1 它为什么长成"CLI + daemon + 扩展"这样

官方链路（README 与架构文档）：

```
AI Agent → bsk CLI → 本地 daemon ⇄127.0.0.1 WebSocket⇄ 浏览器扩展(MV3) → Agent Window → 页面
```

核心不在"能点网页"，而在**登录态怎么来**：扩展跑在用户已登录的 profile 里，所以操作天然继承 Cookie——**一个字节的凭据都不需要搬**。配套三个设计值得抄：

| 设计 | 做法 | 解决什么 |
|---|---|---|
| 双窗口分流 | 默认新开独立 Agent Window（不抢焦点），用户的窗口不动 | Agent 乱点不会碰掉你正在写的文档 |
| 受控借调 | 要动你已有的标签页必须显式 `tab borrow`，且需你确认，用完归还 | 权限最小化，类似"临时门禁卡" |
| Human-in-the-loop | 遇登录/验证码/OTP/支付，`request-help` 交还控制权，人处理完再继续 | 不在死循环里硬闯，这是能上生产的关键 |

还有一点常被忽略：**它不用纯视觉坐标**。`observe` 返回页面文本 + 控件 + `@e3` 这类元素引用，后续针对语义元素操作。这和第十节「UIA 树优先、像素兜底」是同一个判断——纯截图点坐标又贵又脆。

### 12.2 关键前提：Chrome 136 把 CDP 的门关上了

它为什么不用 CDP？不是不想，是**Chrome 不让**。

> 自 Chrome 136 起，`--remote-debugging-port` / `--remote-debugging-pipe` 在**目标为默认数据目录**时不再生效。即使参数被解析，监听端口也不会起，`DevToolsActivePort` 文件不生成。官方给出的理由是安全：攻击者的本地进程可以刷 `/json/version` 偷走已登录 Cookie。Chrome 148 实测仍如此。

本机 Chrome 是 `156.0.8078.48`，早已过了这条线。所以「挂个调试端口让 Playwright/Puppeteer 接管我日常那个浏览器」这条路**已经死了**——除非换 `--user-data-dir` 指向独立目录，但那样登录态就没了，等于白干。

这就是为什么 2026 年这一批方案（BrowserSkill、browser-bridge、mcp-chrome、chrome-use）**全部改走浏览器扩展**：扩展是 Chrome 官方为"在正常 profile 里做事"设计的那条路。

### 12.3 但 ORB 不需要走这条路——它自己就是 Chromium

这是本节最重要的判断。BrowserSkill 那一整套（扩展 + daemon + 自定义协议 + 配对/吊销）存在的唯一理由，是**宿主 Agent 自己没有浏览器**，只能借别人的。而 ORB 是 Electron 应用，手里就有一个 Chromium。

而且基础条件本来就是齐的：

```
grep -c "new BrowserWindow" main.js      → 9        （窗口能力现成）
grep "partition:\|fromPartition" main.js → 0 条     （还没用分区，得加）
grep "webContents.debugger" main.js      → 0 条     （还没用 CDP，可用）
main.js:2250                             → "令牌族只能由主进程 executeJavaScript 推进来（CDP 求值不受 CSP 约束）"
main.js:31 / :46                         → app.setPath("userData", …/.orbdata)
```

最后这条注释说明：**项目里早就在用 CDP 求值了**，只是没把它当成一项能力来用。

### 12.4 实测：三条核心假设全部成立

写了个最小探针 `docs/_webprobe/`，用 ORB 自带的 Electron 44.4.5 跑两个独立进程：

| 验证项 | 结果 |
|---|---|
| 独立分区写 Cookie | `[cookies] count=1 orbprobe=v-1793548562560` |
| **换新进程再读** | `v-1793548562560` —— **一模一样，跨重启持久** |
| 加载外部站点 | `[title] Example Domain` |
| `executeJavaScript` 改 DOM | `[inject] ok` |
| 页面上下文可读状态 | `[doc.cookie] orbprobe=v-…` |
| `webContents.debugger.sendCommand` | `[cdp] {"value":2}` —— **可用，不受 Chrome 136 限制** |
| `capturePage()` | `[capture] 1329x957` |

结论：**ORB 用 `persist:web` 分区 + BrowserWindow，就能做到 BrowserSkill 的核心能力，不需要扩展、不需要 daemon、不需要自定义协议、不需要配对**。CDP 那条在外部 Chrome 上被封的路，在自家进程里完全通畅。

一个必须记的坑：跑探针时 `require('electron')` 报 `Cannot find module`，根因是宿主环境注入了 **`ELECTRON_RUN_AS_NODE=1`**，把 electron.exe 退化成了纯 Node。必须 `env -u ELECTRON_RUN_AS_NODE`。生产启动器同理，别被这个变量坑。

### 12.5 两条落地路线

| | A. ORB 内置浏览器 | B. 借用 BrowserSkill / mcp-chrome |
|---|---|---|
| 登录态来源 | ORB 自己的 `persist:web` 分区 | 用户现有 Chrome profile |
| 用户成本 | **在 ORB 里登录一次**，之后长期有效 | 零登录，但要装 CLI + 扩展 |
| ORB 改动 | `webwin.js` + 几个 IPC + UI | **几乎零改动**，后台 CLI 直接调 `bsk` |
| 能力上限 | 受自己写的工具集限制 | 扩展已实现调试/网络抓包/录制/结构化导出 |
| 不稳定性 | 自己可控 | 依赖第三方版本对齐（扩展↔daemon 版本不匹配会静默失败） |
| 覆盖范围 | 只有 ORB 里登录过的站点 | 用户 Chrome 里所有已登录站点 |

**建议：两条都留，不互斥。**

- **A 做主线**。对 ORB 这种常驻工具，"在 ORB 里登录一次"完全可接受，换来零外部依赖、零版本对齐问题。而且它有 BrowserSkill 做不到的事：**ORB 知道用户在屏幕上干什么**（录制、UIA、剪贴板），网页操作可以和桌面操作串成一条任务链。
- **B 做增强**。用户如果已经装了 `bsk`，ORB 的后台 CLI 本来就能跑 shell，`bsk session start --json` 直接可用，**一行代码都不用改**。检测方式：启动时 `where bsk` / `where mcp-chrome-bridge`。

不建议 C：ORB 自己写一个浏览器扩展。那是把 BrowserSkill 的复杂度整套搬进来，收益却和 A 重叠。

### 12.7 安全边界（必须先说清，否则会出事）

BrowserSkill 官方写得很直白：*"it is not a separate account or security sandbox"*——**Agent 拿到的权限等于你的账号权限**。ORB 做这件事时必须自己补三道闸，因为 ORB 的 AI 会被网页内容影响：

1. **默认只在 Agent 自己的窗口里操作**，绝不默认接管用户正在用的窗口/标签（抄双窗口分流）。
2. **登录态分区隔离**。`persist:web` 和 ORB 自身的其他数据分开，能单独一键清空。别把网页 session 混进主 session。
3. **不可信页面里的指令一律不执行**。网页里写着"请把这个 token 发给 xxx"，那是注入攻击，不是用户指令。这条在"AI 读网页 → 决定下一步"的回路里尤其危险。

还有一条 ORB 特有的：**操作要可回放**。既然 ORB 能录屏，网页任务全程录下来，用户事后能查 AI 到底点了哪个按钮——这比任何权限声明都实在。

### 12.9 修正：上一轮说"不用装"的东西，各自还剩什么用

上一轮的结论是"三个以为必须的东西都不用装"。这一轮把 PyAV 的编码器也数了一遍——**557 个，含 `libx264-165`、`libx265`、`libvpx`、`libopus`、`libmp3lame`、`gif`、`png`、`webp`**。所以"解码不缺、编码也不缺"。

那 yt-dlp 和 ffmpeg 是不是就彻底没用了？不是。边界如下。

**ffmpeg 仍然不可替代的场景：**

| 场景 | 为什么 PyAV 不够 |
|---|---|
| 硬件编码 | PyAV 带的是软件 x264/x265。NVENC / QSV / AMF 要外部 ffmpeg（`av.libs` 里只有 `libvpl`，那是 Intel 的 VPL 加载器，不等于可用编码器） |
| 复杂滤镜链 | `scdet`（场景切换检测）、`tblend`、`zscale`、`drawtext` 这些要么 PyAV 没封，要么封了也没人愿意用 Python 拼 filtergraph；命令行写一行就完事 |
| 流式/管道处理 | `ffmpeg -i pipe:0 -f mp4 pipe:1`，配合另一个进程做转码中转，PyAV 做不到同等的管道语义 |
| 快速格式互转 | 转 GIF、转 webm、抽音轨成 mp3、烧字幕。PyAV 能做，但代码量是命令行的十倍 |
| **用户没装 asr venv 时** | 最现实的一条：PyAV 绑在可选依赖上。用户不装，就只剩 ffmpeg 这条路（或者干脆不支持） |

一句话：**PyAV 负责"看一眼"，ffmpeg 负责"做出来"。** 我们只需要看，所以主路径不需要后者；一旦要做成品（压缩后发给别人、转格式、烧字幕、录屏后处理），ffmpeg 立刻变刚需。

**yt-dlp 仍然不可替代的场景：**

| 场景 | 为什么自己写不够 |
|---|---|
| 长尾站点 | B 站两步 HTTP 搞定，但 YouTube / 抖音 / 小红书 / X / Vimeo 各有各的签名、加密、分片、DRM 前置。yt-dlp 有 1800+ extractor 且在持续跟进改版 |
| **拿现成字幕** | 最被低估的一条：`--write-subs --sub-langs zh-CN` 直接拿 UP 主上传的字幕或平台 AI 字幕，**比跑 whisper 又快又准**（专有名词不会错）。这次那个视频 `subtitle.list` 是空的，但大量视频有 |
| 已下载缓存复用 | `--download-archive` 去重，不重复下载 |
| 站点改版后的兜底 | 我们自己的 B 站解析一旦被改版打死，yt-dlp 通常几天内就修好 |

所以更准确的表述是：**主路径不需要它们，但它们各自覆盖了主路径够不到的一角**。工程上正确的做法不是"永不引入"，而是"默认不引入，遇到边界时按需降级调用，且检测到就告知用户"——和 11.9 第 3 条对 asr venv 的处理是同一个原则。

## 十三、两个新 UI + 凭据保管 + 产物体系（方案，未动代码）

需求三件：① 加一个子页面填网址/账号/密码并加密保护；② 主功能栏加按钮，弹窗输入视频链接或本地文件、优先解析；③ 说清视频识别的产物有哪些、怎么存。

### 13.1 先说一个必须澄清的冲突：你可能不需要存密码

第十二节刚实测过：`persist:web` 分区的 Cookie **跨进程持久**。也就是说用户只要在 ORB 的浏览窗口里手动登录一次，之后 AI 就能一直用——**不需要任何密码**。

所以"填账号密码"这件事要先问清用途，否则会凭空造出一个高风险的数据资产：

| 用途 | 存密码有必要吗 | 更好的做法 |
|---|---|---|
| 免登录浏览、让 AI 操作后台 | **没必要** | 登录一次，Cookie 长期有效（已验证） |
| 登录态被踢/过期后自动重登 | 有一点用 | 但验证码、短信 OTP、扫码会卡住，成功率不高 |
| 首次登录自动填表（省手输） | 有用 | 系统密码管理器也能做，不必 ORB 自己存 |
| 多账号来回切 | 有用 | **存多组 Cookie 比存密码安全**（Cookie 可单条吊销） |

**建议：默认不存密码，把"账号密码"降级成一个可选开关（默认关）**，主路径靠 Cookie。如果确实要存，下面这套是安全的做法。

### 13.2 加密：不要自己发明协议，用系统的

先认清现状——**现在 `orb-state.json` 里的 API Key 就是 49 字符明文**：

```
vision.primary: {provider, baseUrl, model, apiKey(49字符明文), extra}
vision.backup : 同上
```

`grep -rn "safeStorage" orb/desktop/*.js` → **0 条**，全工程从未用过系统加密。

**"加密协议"这个词容易把人引向自研 AES + 自己管密钥，那是错的**——密钥存哪、怎么派生、怎么轮换，每一步都会出错。正确做法是用操作系统提供的凭据保护：

```js
const { safeStorage } = require("electron");
// Windows 上底层是 DPAPI，密文绑定「当前 Windows 用户 + 当前机器」
const cipher = safeStorage.encryptString("password");      // -> Buffer
const plain  = safeStorage.decryptString(cipher);          // -> string
```

落地要点：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 存哪 | 独立文件 `vault.bin`，**不混进 `orb-state.json`** | state 会被备份/迁移/贴给别人看，凭据必须分开 |
| 前置检查 | `safeStorage.isEncryptionAvailable()` 为 false → **拒绝保存**，不降级明文 | 宁可不存，也不能静默降级 |
| 写入 | 先写 `.tmp` 再 rename（复用现有 `stateFile()+".tmp"` 的模式） | 断电不留半个文件 |
| 记录结构 | `{id, origin, user, secretCipher(base64), createdAt, lastUsedAt}` | 只存"域 + 用户名 + 密文"，绝无明文 |
| 内存 | 解密结果用完立刻丢，不缓存到 state | 防止一处泄漏全场泄漏 |
| 能力边界 | 换机器/重装系统解不开 | **这是特性不是 bug**，要在 UI 上写明 |

顺带建议：既然要动这块，**把 `vision.apiKey` 也一起收进 `vault.bin`**（需要一次迁移：首次启动读到明文 → 加密 → 从 state 删除）。否则"密码加密了、API Key 还是明文"是自欺欺人。

### 13.3 子页面放在哪（交付的一部分，不能含糊）

现有 9 个设置页签（`#setnav` 的 `data-pane`）：

look 外观 / vision 视觉模型 / voice 语音 / rec 截屏与录屏 / safe 安全 / chan 通道 / storage 存储 / about 关于 / persona 个性

**新增 `data-pane="vault"`，排在 `safe`（安全）之后、`chan`（通道）之前**——语义相邻，用户找"安全相关"时会看到。

### 13.4 入口按钮放在哪

主功能栏 = 输入框那一行（`panel.html:3196` 附近的 `.chip` 组）。现有顺序是：

```
[rfront 前台] [rvision 视觉] [rback 后台]  ← spacer →  [#attach 附件] [#send 发送]
```

**新按钮插在 `#attach` 左边**，同样用 `chip withico` 的风格（和三个路由 chip 一致），图标用胶片/播放框。理由：它和 `#attach` 语义最近（都是"给 Agent 喂素材"），放一起不会打乱已有的三路由分组。

**不要新开 BrowserWindow。** 用面板内的浮层（参考现有 `#wfMask` 的做法）。理由很实际：新窗口接主题要三处齐（`pushThemeVars()` 窗口数组 + `loadFile` 后推一次 + 令牌表），还要管焦点和生命周期；而这个弹窗内容简单，不值这个成本。

### 13.5 弹窗怎么工作

一个输入框，识别三种输入，**不要做三个 tab**：

| 用户输入 | 识别 | 后续 |
|---|---|---|
| `D:\...\a.mp4` 或拖入文件 | 扩展名 + `fs.existsSync` | 直接进探底，无网络等待 |
| `https://b23.tv/xxx` / 含 BV 号的整段分享文案 | 正则 + 302 跟随 | 先取元信息（数百毫秒），再问是否下载 |
| `https://其他站/...` | 协议头 | 走通用路径，无解析器时明确告知 |

识别成功显示预览芯片：`标题 · 时长 · 分辨率 · 有无音轨 · 预计耗时`，用户点"开始解析"才真正开工。

**"优先解析"的判定顺序**（这是需求里的关键词，要落实）：

1. **命中缓存** → 秒开，直接显示产物入口，不重复解析
2. **本地文件** → 直接探底 + 扫描，不等网络
3. **链接** → 先元信息后下载；下载中就能先跑 ASR 前置检查
4. **超长（>30 分钟）** → 弹窗里直接提示"约需 N 分钟"，并给"只解析前 10 分钟"的选项，别让用户干等

进度要分段显示（下载 / 探底 / 转写 / 抽帧），每段有独立进度和耗时——这对应本项目已有的教训：**"用户说慢"的链必须分段打耗时**。

### 13.6 产物体系：四层，各有用处

这是第 3 问的核心。产物按"确定性 → 需要模型"分四层，**只有 L3 花 token**。

**L1 事实层（确定性，0 token，解析必产）**

| 文件 | 内容 | 大小量级 |
|---|---|---|
| `meta.json` | 来源(URL/路径)、标题、时长、分辨率、帧率、编码、**有无音轨**、解析时间、解析器版本 | < 2 KB |
| `probe.json` | PyAV 探底原始输出（流清单、time_base、码率） | < 2 KB |
| `transcript.json` | ASR 分段 `[{t, e, text}]` + 语言 + **来源标记**(`asr`/`platform`/`caption`) | 10 分钟视频约 30–60 KB |
| `frames/f0000.jpg…` | 索引帧 640×400，间隔 `clamp(duration/40, 3, 30)` 秒 | 每帧约 46 KB，40 帧约 1.8 MB |

`transcript.json` 里那个 `来源标记` 很重要：平台字幕、UP 主字幕、本地 ASR 的置信度完全不同，后面引用时要能区分。

**L2 可读层（给人看，也是喂 Agent 的主料）**

| 文件 | 内容 | 用途 |
|---|---|---|
| `timeline.md` | `[00:15] 这句话…` 逐行时间轴 | **直接拼进 task 文本**，Agent 读这个就够答大部分问题 |
| `index.md` | 帧目录：`[00:15] → frames/f0004.jpg` + 该帧 OCR 文字 | Agent 据此决定"要看哪一帧" |

`timeline.md` 是整个体系的枢纽：纯文本、token 便宜、模型可直接引用。10 分钟视频约 4000–6000 字，塞得进任何上下文。

**L3 结论层（消耗 token，按需生成，不解析时不做）**

| 文件 | 内容 | 触发 |
|---|---|---|
| `report.md` | 模型总结（分章节 + 时间戳引用） | 用户问"讲讲这个视频" |
| `skill.md` | 可复用操作手册（第十节精华 4） | 任务是操作类，且用户要"以后照做" |
| `evidence/` | 被 report 引用的证据帧（原分辨率单帧） | 生成 report 时顺手存 |

**L4 原始层（可选，占地最大）**

| 文件 | 内容 | 策略 |
|---|---|---|
| `media/v.m4s` `a.m4s` | 下载的原始流 | 默认**保留 7 天**，可设为"解析完即删" |
| `media/source.mp4` | 本地文件的软链接/记录（不拷贝） | 只记路径，不复制 |

### 13.7 存放、清理、导出

```
<userData>/vidx/                     ← userData 已被 setPath 指到 .orbdata
  bili_BV1P73G6zENo_p1/
    manifest.json     ← 产物清单 + 各自大小 + 生成时间 + 版本
    meta.json  probe.json
    transcript.json  timeline.md  index.md
    report.md  skill.md
    frames/f0000.jpg …
    evidence/
    media/            ← L4，可删
  bili_BV1xx_p2/      ← 分 P 独立，绝不合并
  local_<sha1>_<mtime>/
```

四条保存原则：

1. **全部本地，不上传**。产物里可能含账号、内网地址、屏幕内容，绝不能进任何云。
2. **JSON 一律原子写**（复用现有 `.tmp` + rename 模式），断电不留半个文件。
3. **清理只清 L4**。L1–L3 加起来通常 < 3 MB，留着几乎不占地方；真正占地的是 `media/`。默认上限 4 GB，超了按 `manifest.json` 的生成时间淘汰整个 key 目录。
4. **可导出**。一个"导出"按钮 → 打包 zip（`timeline.md` + `index.md` + `report.md` + `frames/`，不含 `media/`），用户能带走。这也是本项目一贯的做法：产物要能离开应用还存在。

### 13.8 产物怎么进入对话（这一步决定好不好用）

| 场景 | 做法 |
|---|---|
| 短视频（< 10 分钟） | `timeline.md` 全文拼进 task 文本 —— 几千字，模型直接答 |
| 长视频 | 先给 `index.md`（帧目录 + 每帧一句话），模型自己决定看哪段 |
| 问到具体画面 | 取对应帧，**原分辨率单帧**（不是缩略图）作为图片喂视觉槽位 |
| 问到连续动作/操作过程 | 原生视频切片 ≤ 2 分钟，走已实测可用的视觉槽位 |

注意一处一致性：`timeline.md` 和 `index.md` 里的时间戳必须同源（都来自 `transcript.json` 和帧的实际 `pts`），否则模型引用会错位——第十一节 11.6 那个 `seek` 微秒单位坑，本质就是这个问题的另一面。

### 13.9 工程量

| 模块 | 内容 | 量级 |
|---|---|---|
| `panel.html` | 新页签 `vault` + 新浮层 + 主功能栏按钮 | 中 |

### 13.10 三件需要你拍板

## 十四、音频识别：单独音频与视频音轨（2026-11-02 实测）

问题：不管音频是独立文件，还是藏在视频里，这套方案能不能识别？**能，而且是同一条管道，不需要分两套代码。**

### 14.1 实测：六种输入，五种格式全过

素材用 `voicepack` 里的 opus 台词（真值已知），8 段拼成 9.08 秒，用 PyAV 转成各格式后逐个喂 faster-whisper（small/int8/CPU，模型已加载）：

真值：`回来了，位置给你留着。 / 你去哪儿了，进度我先盯着。 / 回来就好，随时继续。 / 我把要点都记下来了。`

| 输入 | 结果 | 耗时 |
|---|---|---|
| `sample.wav` | 回来了,位置给你留着。你去哪儿了?进度我先盯着。回来就好。随时继续,我把要点都记下来了。 | 2.51s |
| `sample.mp3` | 同上（标点略有差异） | 2.32s |
| `sample.flac` | 同上 | 3.24s |
| `sample.m4a` | 同上 | 2.65s |
| **`sample.opus`** | 同上 | 2.52s |
| **`with_audio.mp4`**（视频+音轨） | 同上，**直接转写，不用先抽音轨** | 2.84s |

只有一段 `我` 字是识别时多出来的（TTS 合成的起始音），四句主体全对。**格式不影响结果，音质才影响。**

### 14.2 为什么格式无所谓

`asr_server.py:377` 那段按后缀分派（`.wav` / `.mp4` / `.m4a`，其余落到 `.webm`）**只决定临时文件叫什么名字**。faster-whisper 内部用 PyAV 打开，靠**内容嗅探**判断真实容器——所以：

- `.opus`、`.flac`、`.mp3` 全都落进 `.webm` 分支，照样能解；
- 第十一节那个 `.m4s` 也落进 `.webm` 分支，照样能解。

结论：**这段分派逻辑是"侥幸正确"**——它不会失败，但也没起作用。真要改，应该按内容（`av.open` 探测）而不是按文件名，或者干脆不猜、统一用 `.bin` 让 av 嗅探。（当前不动代码，只记结论。）

### 14.3 但有一个必须前置拦截的坑：无音轨视频

同一个探针，拿 `_v8min.mp4`（ORB 自己录的，**没有音轨**）直接喂：

```
探底: dur=480.00s  video:h264 480x270          ← 只有 video 流
ASR 失败: IndexError: tuple index out of range  ← faster-whisper 内部找不到音频流
```

这个报错**完全不可读**，用户只会看到"识别失败"。所以管道里必须先探底：

```
if (meta.hasAudio === false) → 直接提示"这段视频没有音轨，识别不了语音"
                              → 可选：转去做画面理解（第十一节 L2/L3）
```

这正是产物 L1 里 `meta.json` 必须记 `hasAudio` 的原因——它不是装饰字段，是**分流开关**。

顺便说明它为什么重要：第十一节已确认 ORB 录制的视频全都无音轨（`orb-cap.c` 零音频代码，`panel.html` 是 `audio:false`）。所以"用户丢进来一段自己录的片子，问 AI 讲了什么"这个最常见的场景，**当前必然走到这个 IndexError**。探底拦截是必须的，不是优化。

### 14.4 管道：音频和视频走同一条路

```
任何输入（mp3 / wav / m4a / flac / opus / mp4 / mkv / m4s / …）
        │
   [探底] PyAV 一次 open
        ├─ hasAudio=false → 提示"没有音轨"，转画面理解或直接退出
        └─ hasAudio=true  → 直接进 ASR（不用抽音轨、不用转码）
        │
   [转写] faster-whisper，输出 [{t, e, text}]
        │
   [分叉] 有视频流 → 继续跑扫描抽帧（第十一节 L2/L3）
          纯音频   → 跳过抽帧，直接出 timeline.md
```

**不需要"先分离音轨"这一步**。很多方案会先 `ffmpeg -vn -acodec copy` 抽一遍，这里没必要——whisper 自己会找音轨，抽一遍只是多一次 IO。

### 14.5 纯音频时产物体系怎么变

对照 13.6 的四层，纯音频少两样：

| 层 | 视频 | 纯音频 |
|---|---|---|
| L1 事实 | `meta.json` / `probe.json` / `transcript.json` / `frames/` | 前三样照旧，**无 `frames/`** |
| L2 可读 | `timeline.md` / `index.md` | **只有 `timeline.md`**（没有帧可索引） |
| L3 结论 | `report.md` / `skill.md` / `evidence/` | `report.md` 只能基于文字，**无 `evidence/`** |
| L4 原始 | `media/` | 原文件只记路径，不拷贝 |

对播客、会议录音、课程音频这类内容，纯文字**正好够用**——它们的信息本来就在语言里，不在画面上。反倒是 `timeline.md` 更重要了：没有画面兜底，文字稿就是唯一证据。

### 14.6 四个真实边界（别过度承诺）

| 边界 | 实际情况 | 应对 |
|---|---|---|
| **唱歌/音乐** | whisper 是**语音**模型，唱歌识别会糊成一团；歌词、说唱基本不可用 | 明确告知"能识别说话，不识别歌词"；别拿它做音乐转写 |
| **多说话人** | whisper **不做说话人分离**（diarization），输出是连续文本，分不清谁在说 | 会议场景需要额外模型（如 pyannote）；当前版本只能说"这是文字稿"，不能说"谁说的" |
| **长音频** | 0.2× 实时：1 小时音频约需 12 分钟（CPU/small） | 必须后台任务 + 分段进度 + 可取消；别做成同步等待 |
| **强噪声** | `vad_filter=True` 会跳过静音，但持续噪声会显著拉低准确率 | 转写结果标注"低置信"，别当成逐字准确 |

其中"多说话人"这条最容易造成预期落差。产品文案上应该写"**转写文字稿**"，而不是"**会议纪要**"——后者隐含了说话人归属。

### 14.7 顺带确认的两件事

1. **`recAudio` 确实是半成品**。`main.js:5437` 的 `set-recaudio` 只把 `none|system|mic|mix` 落盘，**从未传给 `orb-cap.exe`**（`cap-native.js` 的 args 只有 `--rect`），`orb-cap.c` 里零 WASAPI。所以设置页那个"录屏音频来源"选项是**有 UI 没采集**——用户选了也不会生效。补音轨时 UI 那一半已经现成。
2. **voicepack 的 360 条 opus 可以直接当测试语料**。它们在 `orb/desktop/voicepack/*.opus`，真值文本在 `voicepack/index.js`（`{台词: 文件名}` 的映射），做 ASR 回归测试不用另找素材。

### 14.8 探针

`docs/_audio_probe.py`（三个模式，可复跑）：

```
asr\venv\Scripts\python.exe docs\_audio_probe.py build        # 拼素材，出 wav/mp3/flac/m4a/opus
asr\venv\Scripts\python.exe docs\_audio_probe.py probe <文件>  # 探底：时长/采样率/声道/有无视频
asr\venv\Scripts\python.exe docs\_audio_probe.py asr <文件>    # 直接转写
```

## 附：结论

**能力已实测通过，模型不需要新增**：现有备选槽位 `glm-4.1v-thinking-flash` 直传 base64 视频返回 200，5 分钟与 8 分钟片子的时间定位精确命中。这条能力保留，用于 L4。

**主路径经过三轮修订，从"看全片"一路收敛到"按来源分叉"**：

| 版本 | 主路径 | 被什么否掉 |
|---|---|---|
| v1 | 原生视频直传 | 算术：1080p 下 64K 上下文只装 43 秒 |
| v2 | 关键帧总览图铺全片 | 实测 + 论文：拼图只省 32% token，网格化破坏空间邻接、多图干扰使准确率系统性下降 |
| v3 | 文本先行 + 按需取帧 | 仍然默认"只能看像素"，漏掉了录制时机 |
| **v4** | **按来源分叉：自录的走 UIA 时间轴，外部的走文字+证据帧** | 当前方案 |

四件工程活，按性价比排序：
1. **L1 文本索引**（复用现成 `asr/`）——地基，零成本；
2. **录制时的事件 JSONL**（点击/切窗/焦点/UIA 片段）——**只在录制瞬间可采，事后补不回来，优先级高于任何抽帧优化**；
3. `/api/vlm` 的 `max_tokens` 1024 → **4096**，剥 `<think>` / `<answer>` / `<|begin_of_box|>`，证据帧分开传、单批 ≤8；拼图只用于导航；
4. 产出加一份 `SKILL.md`——把"看懂了"升级成"能复用"。

一句话：**自录的靠事件时间轴，外部视频靠文字找位置、单帧看证据、原生看动作。**

**第 7 轮补充（输入解析）**：用户丢链接或丢文件，控制台能不能自己解析——**能，且不需要新增任何外部依赖**。

| 环节 | 结论 | 依据 |
|---|---|---|
| B 站取流 | 两步 HTTP 搞定，无需 yt-dlp | `view` → `playurl` 实测 `code=0`，短链 302 自动跟随 |
| 音视频合并 | **不需要** | `.m4s` 各自 `av.open()` 成功，duration 与实际一致 |
| 解码器 | 不必打包 ffmpeg（省 100MB） | `asr/venv` 里 PyAV 18.1 + FFmpeg 62 全套 `.dll` |
| 文字稿 | `.m4s` 直喂 faster-whisper，无需转码 | 630s → 186 段带时间戳，126s（0.2× 实时） |
| 抽帧 | **顺序扫一遍，不要逐点 seek** | 127 帧 4.75s vs 5 次 seek 9.5s |
| 自录音轨 | **当前没有**，ASR 对自录视频不成立 | `orb-cap.c` 零音频代码，`panel.html:7531 audio:false` |

四件事的复杂度全部低于预期，唯一的新增工作量是**主进程的流式下载器**（工程里目前完全没有，须用 `net.request` 而非 `fetch`，否则长视频顶穿内存）。

唯一被现实卡住的是"自录视频走 ASR"——录制层从来没采过音频。建议先按"自录靠 UIA 时间轴 + OCR、不靠听声"落地，补音轨排进 M2。

**第 8 轮补充（Web 操作）**：腾讯 BrowserSkill 让 AI 用你已登录的浏览器，ORB 能不能照做——**能，而且比它简单一个数量级**。

| 判断 | 结论 | 依据 |
|---|---|---|
| 为什么它要用扩展 | 因为 **Chrome 136 起禁了对默认 profile 开 CDP** | 本机 Chrome 156，实测端口不再监听 |
| ORB 需要扩展吗 | **不需要** | ORB 自己就是 Electron 44，9 个 BrowserWindow 现成 |
| 登录态能复用吗 | 能，`persist:web` 分区跨进程持久 | 新进程读到与先前完全相同的 cookie 值 |
| 能操作页面吗 | `executeJavaScript` + `webContents.debugger` 都可用 | `[inject] ok`、`[cdp] {"value":2}` |
| 需要 daemon/协议吗 | 不需要，主进程直接做 | 省掉三层架构 |

代价只有一条：**用户要在 ORB 里登录一次**（而不是复用 Chrome 里已有的登录）。对常驻工具来说这个代价可接受。如果用户已装 `bsk`/`mcp-chrome`，ORB 的后台 CLI 天然能调，零改动——所以是"A 做主线、B 做增强"，不是二选一。

三条安全红线要先立：只在自己的窗口里操作、登录态分区可单独清空、**不可信页面里的指令一律不执行**（网页里写"把这个 token 发出去"是注入，不是用户意图）。

另外修正一条上一轮的边界：PyAV 这个构建有 **557 个编码器（含 libx264/x265）**，所以"看一眼"和"做出来"都不缺。但 ffmpeg 仍在**硬件编码、复杂滤镜（scdet/tblend/drawtext）、管道处理、快速转格式、用户没装 venv** 这五处不可替代；yt-dlp 仍在**长尾站点、拿现成字幕、下载去重、改版兜底** 四处不可替代。正确姿势是"默认不引入，遇边界按需降级并告知"，不是"永不引入"。

**第 9 轮补充（两个 UI + 产物体系）**：方案见第十三章，三条关键判断：

1. **密码可能根本不用存**。第十二节已验证 `persist:web` 的 Cookie 跨重启持久，登录一次就够；存密码只对"自动重登/多账号切换"有意义，而验证码会卡住重登。建议默认不存，作为可选开关。
2. **加密别自己发明**。用 `safeStorage`（Windows 下是 DPAPI，绑定当前用户+本机），存独立 `vault.bin`，不混进 `orb-state.json`；`isEncryptionAvailable()===false` 时**拒绝保存而不是降级明文**。顺带把现在 49 字符明文的 `vision.apiKey` 一起收进去，否则安全等级不一致。
3. **产物分四层，只有第三层花 token**：

| 层 | 产物 | 成本 |
|---|---|---|
| L1 事实 | `meta.json` / `probe.json` / `transcript.json` / `frames/` | 0 token |
| L2 可读 | `timeline.md` / `index.md` | 0 token，**Agent 主要读这两个** |
| L3 结论 | `report.md` / `skill.md` / `evidence/` | 按需才生成 |
| L4 原始 | `media/` | 占空间，可设立即删 |

存放 `<userData>/vidx/<key>/`，分 P 独立、JSON 原子写、清理只清 L4、可一键导出 zip（不含 media）。

**第 10 轮补充（音频识别）**：不管音频独立存在还是藏在视频里，**都能识别，且是同一套代码**。实测六种输入：

| 输入 | 结果 |
|---|---|
| wav / mp3 / flac / m4a / **opus** | 全部识别正确（四句台词全对，仅多一个起始"我"） |
| **带音轨 mp4** | **直接转写，不需要先抽音轨** |
| **无音轨 mp4** | 抛 `IndexError: tuple index out of range`（不可读） |

三条结论：

1. **格式无所谓**。`asr_server.py:377` 那套后缀分派只决定临时文件名，faster-whisper 靠 PyAV 内容嗅探——所以 `.opus`/`.flac`/`.mp3` 落进 `.webm` 分支也能解。这段逻辑是"侥幸正确"。
2. **必须前置探底判 `hasAudio`**。否则无音轨视频会给用户一个看不懂的 `IndexError`。而 ORB 自己录的视频**全都无音轨**，所以"丢进来自录视频问讲了什么"这个最常见场景当前必然翻车——探底拦截是必需的，不是优化。
3. **纯音频产物少两样**：无 `frames/`、无 `evidence/`，`timeline.md` 成为唯一证据。对播客/会议/课程正好够用。

四个边界别过度承诺：**唱歌识别不了**（whisper 是语音模型）、**不做说话人分离**（分不清谁在说，别写"会议纪要"）、**0.2× 实时**（1 小时音频 12 分钟，必须后台+进度）、**强噪声准确率骤降**。

顺带确认：`recAudio` 是**有 UI 没采集**的半成品（`set-recaudio` 只落盘，从未传给 `orb-cap.exe`）；`voicepack` 的 360 条 opus 可直接当 ASR 回归语料（真值在 `voicepack/index.js`）。
