# ORB 控制台 × DeepSeek Super-agent：改造方案

> 评估基准：本仓库 **v1.4.7**（2026-11-02，含 SenseVoice 情绪、旋转屏/HDR 录制、录制音频、看视频管道）。
> 参照材料：DeepSeek Harness 团队 2026-10-31《Super-agent 设计探索：迈向更自主的 Agent 系统》+ 开源研究原型 `dsh-superagent-prototype`；
> 以及基于 `zhoukr123/ORB-Console-made-for-workbuddy` **v1.4.5** 包做的《ORB 控制台优化方案总报告》。
> 本文只回答三个问题：**它是什么、ORB 能不能启动、按什么顺序改**。

---

## 0. 一句话结论

**架构可以迁移，部署形态不能迁移。** 真正值得抄的是三样东西：**两级过滤（程序先筛、模型再判）+ 订阅直通（同一 Thread 后续事件不再经过路由）+ 每张工单的预算与副作用账本**。
而"云端常在线 / 存算分离 / N 个 Worker 随便开 / A2A"这四件，在**桌面单用户 + GUI 全局单例 + 零遥测**的定位下全是负资产。

改造顺序也定死：**先让"停在哪、恢复从哪开始"说得清（P0）→ 再有一把能量出收益的尺子（P1）→ 才谈路由（P2）→ 最后才并发（P3）**。
先加 Worker 等于在账单上乘以 N，而在没有评测数据的情况下，你无法证明它变快了。

## 1. Super-agent 到底是什么（只记事实，不记宣传）

| 项 | 事实 |
|---|---|
| 发布时间 | 2026-10-31 晚（DeepSeek Harness 团队公众号 + 技术文章） |
| 发布物 | **一套架构** + MIT 协议研究原型 `dsh-superagent-prototype`（v0.1.0，单 commit 216 文件）。**不是新模型** |
| 核心命题 | 人只能同时跟 3~5 个会话，多任务瓶颈已从"模型能力"转到"人的注意力"；Session 应从用户概念降为系统实现细节 |
| 结构 | Router（常驻全局协调，长输入短输出，可不配 Bash）+ Worker（各自隔离上下文，可再调 Subagent） |
| 事件 | 一切外部输入都是 Trigger：群聊、邮件、日程、PR 评论、CI 结果 |
| 过滤 | **两级**：程序层查来源/群组/白名单（不耗模型）→ 模型层按提示词判是否行动 |
| 直通 | 同一 PR / IM 话题 / 邮件串 = 一个 Thread；首次由 Router 建 Worker + 订阅，**后续事件程序直接投给已订阅的 Worker** |
| 上下文 | Inline & Spill（窗口当 Cache）+ 链式召回（每个对象带 ID，每次读取返回下一跳入口） |
| 主动性 | 投机执行：群里有人报 Bug，后台先复现，确认存在且修法简单才提交，否则**全程保持安静** |
| 交互 | 异步 ReAct：`start()` 立即返回 Started，结果作为新事件回投；`stop()` 可掐。**官方承认已在 Harness 实现但默认没开** |
| 运行 | 计算（云端无状态容器）+ 状态（DB）分离；执行环境留本地，只放不存状态的轻量 daemon |
| 自愈 | 独立 Watchdog Session，定时消息驱动，判"有没有实质进展"而不只是"进程活着" |
| 官方数字 | 300 条消息 / 20 项工作请求 / 每组 5 次合成负载：p50 **12.4** 分钟、p95 **15.7** 分钟；单 Session 中性提示基线 p50 20.4 / p95 29.5。去掉订阅直通 → Router 决策数 **+30%**、读缓存 Token 2323 万 → 3177 万（**+37%**）。批处理把单次决定推理 6.4s → **1.6s** |
| 官方局限 | 原型主要面向**单个 GitHub 仓库**；部分设计未实现；社区里没有针对该仓库的 PR 级改造补丁 |

**六个部件里，只有两个是"新思想"**：投机执行、异步 ReAct。其余（双层分工、事件驱动、快慢路径、批处理、订阅、存算分离、外部 Watchdog）都是经典系统工程在 Agent 上的落点。这一点很重要——意味着 **ORB 不需要重写，只需要把已有控制面接上这些契约**。

## 2. 那份优化报告的可信度：方法可信，结论有三条已过时

报告的做法是稳的：两次下载 main 包比 SHA256（一致）、逐目录 diff、引用精确到 `文件:行号`。这种"只承认 main"的纪律值得保留。

但它写于 **v1.4.5**。以下三条在 v1.4.7 上**已经不成立**，直接引用会得出错误结论：

| 报告判断（基于 v1.4.5） | v1.4.7 实际 | 结论 |
|---|---|---|
| 附件上限 100 MB（`main.js:2481`） | `ATTACH_MAX_SIZE = 1024*1024*1024`（1 GB，`main.js:2545`） | **已过时** |
| `orb-cap.c:48` "无音频"，合流链路未闭环 | 1.4.6 起 WASAPI 环回 + 麦克风双路合流，实测 AAC-LC 48k 立体声、A/V 差 8~12ms | **已过时** |
| main 未检出抽帧/逐帧视觉分析 | `orb/desktop/vidx.js` + `vidx_probe.py` 已有完整管道（探底/抽帧/台词/时间线） | **已过时** |

仍然成立、且是要害的三条（已复核 v1.4.7）：

- `STOP_EXEMPT` 仍含 `workbuddy|workbuddy_execute`（`bridge.mjs:2888-2896`）——急停期间仍可新建后台思考；
- 急停文案仍是"不影响已派发的后台任务"（`SECURITY.md:21`、`panel.html:3194/3790`、`STOP_SCOPE_NOTE` 在 `panel.html:15285`），
  而 `doStop()`（`bridge.mjs:2092-2103`）实际会 `killActiveProcs()` 杀掉子进程树。
  注意这段文案是 **2026-10-13 用户明确决策**"只补文案、不改行为"的产物（见 `BUGFIX-渲染层.md:23`），
  当时描述是对的；后来急停的行为扩到了后台，文案没跟着改——这不是笔误，是决策过期；
- `ROADMAP.md:6` 仍写"最新发布 v1.0.1 / 待发布 v1.2.0"，落后 6 个版本。

> **所以这份方案的正确用法**：当路线图用，但每个"现状"判断都要在改动前重核一次。它最大的价值不是结论，是那份"代码里到底有什么"的清单。

## 3. 启动可行性：逐项对照

| 维度 | Super-agent 的前提 | ORB 现状（v1.4.7） | 能否照做 |
|---|---|---|---|
| 事件源 | IM / GitHub / 邮件 / CI 多渠道 | 定时、文件变化、热键三类；另有工作流触发器 | **部分可做**：桌面端永远只有这三类，加 IM 需登录态与合规成本 |
| 并发 | 云端容器，Worker 想开多少开多少 | 桌面单用户；鼠标/键盘/剪贴板/焦点是**全局单例** | **只能 1 个持令牌的 GUI Worker + N 个后台/分析 Worker** |
| 状态 | DB + 存算分离 | 本地 JSON + 单进程 + `jobs` Map | 不必抄；本地 SQLite 都算重，JSON + 原子写够用 |
| 凭据 | Agent 不接触凭据本身 | `.bridge.json` 同机可读（`SECURITY.md:26-34` 自认） | **并发会放大风险**，必须先收口 |
| 常在线 | 云端 Agent + 本地轻量 daemon | 热启动 daemon 官方自己说两条路线实测都不稳（`bridge.conf:3-4`） | **不做**，等它稳 |
| 评测 | 合成负载、每组 5 次 | `orb.ttft`（近 30 次 p50/p95）+ 积分弹窗 | **缺**：总时长、p95 分档、每任务成本、错误分派率 |
| 主动性 | 投机执行 + 静默交付 | 无 | 可做，但**必须 observe 起步**，不能直接 auto |
| 安全定位 | 云端隔离实例 | 桌面级、真的操作电脑、零遥测 | 迁移原则，不迁移形态 |

**可行性结论分三档：**

- **立刻可启动（P0 + P1）**：纯本地改造、无新依赖、单人 1~2 周量级、不改变现有执行模型。风险低。
- **有条件启动（P2）**：语义 Router 只能先做 **observe 影子模式**——记录"本来会派给谁"但不建单、不启 Worker。要放开 auto，必须先有归属准确率与误触发率两个数字。
- **暂不启动（P3）**：并发 Worker、A2A、长程 Memory-Ticket 融合。前置条件是 P1 的尺子能量出收益，而现在量不出。

## 4. 改造方案（四批，每批都能独立收工）

### P0 · 控制语义与文档一致（**不改变行为模型，只让"停在哪"说得清**）

| # | 目标 | 落点 | 动作 | 验收 |
|---|---|---|---|---|
| P0-1 | 急停覆盖新建工单 | `bridge.mjs:2888-2896` | 把 `workbuddy|workbuddy_execute` 移出默认豁免；保留 6 项只读观察 | 急停期间调后台派活返回"急停中"；恢复前不新增自动工单 |
| P0-2 | 文档与代码对齐 | `SECURITY.md:21`、`panel.html:3194/3790`、`STOP_SCOPE_NOTE`(`panel.html:15285`)、`BUGFIX-渲染层.md:23` | 统一改为"杀后台 CLI 子进程树、卸触发器、清在途订阅；仅只读观察保留"。**这是 2026-10-13 决策的过期，不是笔误**，改文案前先确认用户是否接受"急停连后台一起停" | grep 旧表述 = 0；面板文案与日志 `已终止 N 个在跑的子进程` 一致 |
| P0-3 | 急停事件化 | `bridge.mjs:3116-3195` | 对受影响任务发 `{type:"stopped",reason,epoch}` 再取消订阅 | streaming 中途急停，前端 1s 内收到 stopped，不再等 final |
| P0-4 | ROADMAP 复位 | `ROADMAP.md:6-7,28-37` | 改为最新 v1.4.7，v1.3/v1.4 标已发布 | 文档与 README 版本一致 |

> 为什么排第一：这三处都是**说一套做一套**。单线程时只是体验问题；一旦有并发，权限误判就是从"一句话说错"变成"一批任务同时越权"。

### P1 · 评测尺子（**没有这把尺子，后面所有优化都无法证伪**）

| # | 目标 | 落点 | 动作 | 验收 |
|---|---|---|---|---|
| P1-1 | 五事件埋点 | `panel.html:4238-4261`（`orb.ttft` 旁）、`bridge.mjs` 任务入口 | 新增 `orb.perf`：dispatch / first_tool_result / first_partial / last_tool / finish | 单任务可回放五事件；TTFT 与总时长分列 |
| P1-2 | 成本记到任务上 | 积分弹窗 + `startJob()` | 每任务记 输入/输出 token、模型、耗时、成败 | 能算出"每有效任务推理成本" |
| P1-3 | 判断表落地 | 文档 + 面板状态行 | 照总报告那张表判收益类型（感知收益 ≠ 真提速） | "TTFT 降但总时长不变"不再被写成提速 |
| P1-4 | 基线固定 | 探针 `docs/_perf_baseline.cjs` | 同任务、同模型、同附件，每组 ≥ 30 次，对照/实验交替 | 有可复现的 p50/p95 基线文件 |

> 为什么排第二：Super-agent 官方是"拿 Token 换时间"。ORB 加任何并发之前，必须先能回答"这一换，值不值"。

### P2 · 语义 Router（**只做 observe 影子模式**）

| # | 目标 | 落点 | 动作 | 验收 |
|---|---|---|---|---|
| P2-1 | 两级过滤（先程序） | 复用 `bridge.mjs:2698-2759` 触发器骨架 | 程序层查来源/白名单/类型/大小/当前 epoch/速率；不通过**不调用模型** | 闲聊类输入零模型调用（看日志可证） |
| P2-2 | 语义判定（后模型） | 新增 `orb/desktop/router.js` | 只看"新建 / 追加到已有工单 / 忽略 / 停"四类判定 | observe 模式只写决策日志，**不建单、不启 Worker** |
| P2-3 | 决策日志可回放 | `<userData>/router/decisions.jsonl` | 记 判定、依据规则、候选工单、拟注入上下文、耗时 | 同一事件可离线重放；误报/漏报可量化 |
| P2-4 | 放行门槛 | 文档 | observe 攒够样本，归属准确率与误触发率达阈值才允许 auto | 达不到就永久停在 observe（这也是个合法结局） |

**明确不做的两件事**：不做跨设备/跨账号路由；不做"未配置也自动接管"——桌面端的默认必须是"不打扰"。

### P3 · 并发形态（**1 GUI + N 后台**，不是 N 个 Worker）

| # | 目标 | 落点 | 动作 | 验收 |
|---|---|---|---|---|
| P3-1 | GUI 仲裁令牌 | `main.js` 前台/视觉入口 | 全局 acquire/release，前台与视觉互斥，人工请求可插队 | 两个视觉任务不争鼠标；前台优先完成再交还 |
| P3-2 | 后台 Worker 额度 | `bridge.mjs:553/3037` | 并发额度与"保留条数"分开；额度可配、默认 2 | 额度满时排队而非静默丢弃 |
| P3-3 | 订阅直通 | 复用 SSE `jobSubs` | 同工单后续事件直投原 Worker，不经 Router | 同 Thread 连续事件只路由一次 |
| P3-4 | 副作用账本 | 新增 `orb/desktop/outbox.js` | id/target/payload/attempts/receipt/epoch/status；只恢复未确认项 | 两个 job 并发急停后副作用可枚举、不重放、不互相覆盖 |

> P3 的准入条件写死：**P1 有基线 + P2 有数字 + P0 全绿**。三条缺一不进。

### P4 · 长程与授权（可选，最小实现）

- **Ticket / Thread / Mandate 与七层记忆分家**：记忆负责"相关且值得回忆"，事务状态负责"不丢、不重放、可审计"。遗忘曲线**不能**管理 Mandate。
- **Mandate 记"为什么可以做"**：授权来源、批准人、规则 id 与版本、适用范围、有效期、预算、撤销条件。规则更新只影响新工单，活跃工单降级为人工复核。
- **不可信输入隔离**：视频画面、网页正文、ASR 转写只进暂存层，指令性内容不得因"自动写入"获得更高可信度。
- **记忆写入加归属**：`worker_id / ticket_id / epoch / 版本号`；急停瞬间正在写入的条目记"中断产生"，恢复后不浮起。

## 5. 明确不搬的五件事

1. **存算分离 + 云端常在线**——与"桌面级、真的操作电脑、密钥不落盘、零遥测"直接冲突。执行体与凭据留在本机是产品定位，不是技术债。
2. **独立 Watchdog Session**——已有 `MAX_DEPTH=8`、`MAX_WHILE=500`、急停、超时 kill、智能接管，边际价值低；且外部 Watchdog 极易把"人为急停"误判成故障再拉起。
3. **A2A / 多实例**——单机单用户没有多 Agent 安全通信的强需求，先做只会引入 Thread 归属、工单去重、策略一致性三个新问题。
4. **把七层记忆直接当事务存储**——艾宾浩斯衰减与浮起会复活已封存工单。
5. **把 Router 拆成多个分片**——分片粒度越细，跨分片上下文连续性越差；官方自己也说单 Router 在团队规模下够用。

## 6. 这次的「台词回顾」怎么变成 P1 的第一个样本

刚落的这个改动（`vidx.js` 的 review 步骤）表面是功能，实际上是 P1 尺子的**第一根刻度**：

- 它把"Agent 读一堆错字自己猜"变成"读干净文本"，**减少的是模型往返与返工**，不是感知延迟；
- 它天然带三个可测字段：`covered / changed / ms`，加上模型名就是一次完整的**每任务成本记录**；
- 失败路径是明确的产品决策：**回顾失败也必须有台词**（先落原始转写再回顾，原文留在 `segments[].textRaw`）。

可以直接用它验证 P1 的判断表：如果"回顾后 Agent 的总时长下降、TTFT 不变"，那是**串行路径压缩**（可纳入基线）；如果只有 TTFT 变，那就是感知收益，不算提速。

## 7. 风险清单

| 风险 | 表现 | 对策 |
|---|---|---|
| 文档继续落后于代码 | 用户按文档理解权限，实际行为更强 | P0 与代码同 PR；发版前 grep 旧表述 |
| 没有基线就上并发 | 变慢但感觉"更先进" | P1 是 P3 的硬前置 |
| observe 期样本不足就放开 auto | 误触发打扰用户，信任一次性耗尽 | 设阈值 + 达不到就永久 observe |
| 凭据面扩大 | 多 Worker 共享 `.bridge.json` | 先做密钥代理/独立账号，再谈并发 |
| 待发布能力被当成已发布 | 按 1GB/音轨/视频写设计，实际 main 没有 | 本次已核对：这三条在 1.4.7 均**已实装**，报告对应段落作废 |
| 参考报告过期 | 引用错误行号 | 引用前重核；本文所有行号均按 v1.4.7 |

## 8. 建议的落地顺序（按周）

1. **第 1 周**：P0 全绿（4 项）+ P1-1 埋点。目标：急停语义一致、五事件可回放。
2. **第 2 周**：P1-2~P1-4 基线 + 用「台词回顾」跑第一组对照（回顾开/关 × 同视频）。目标：一张能证伪的表。
3. **第 3 周起**：P2 observe 影子 Router，只写日志。攒够样本再决定要不要 auto。
4. **P3 明确不排期**：等 P1 数据说话。如果数据显示"单线程瓶颈在视觉重试和记忆召回"，那并发根本不是当前该做的事。
