# 可靠执行 · 对标记录与实施说明

> 这份文档回答两件事：**每一条可靠性设计对标了哪个一手来源、采纳了什么、拒绝什么及为什么**，
> 以及**代码里到底落在哪**。
>
> 写作纪律（三条，缺一条这份文档就会退化成"我们很努力"的清单）：
> 1. **一手来源**：只引官方文档 / 官方博客 / 项目仓库，不引二手总结。
> 2. **只写能落地的**：采纳的部分必须能指到文件和函数。
> 3. **不能落地的要写清为什么** —— 拒绝的理由比采纳的理由更重要，否则下一个人会把
>    "我们没做熔断"当成遗漏，再花一周重新论证一遍。

---

## 0. 一句话结论

桌面自动化的可靠性缺口不在"多写几个 try/catch"，而在四件事：
**动手前知不知道会失败**（预检）、**失败后敢不敢重试**（风险分级 + 抖动退避）、
**中断后能不能安全接着跑**（断点 + 内容指纹）、**跑完凭什么说成功**（三档结论 + 收据）。
这四件事都有成熟的一手方案，逐条对标即可，不需要发明。

## 1. 逐条对标

### 1.1 动手之前先判断能不能动手 — Playwright actionability + n8n 四道门

| 项 | 内容 |
|---|---|
| 一手来源 | Playwright 文档 *Auto-waiting / Actionability*：动作前依次检查 Visible、Stable、Receives Events、Enabled、Editable；n8n 工作流发布四道门：validate → verify connections → test → activate |
| 它解决的问题 | 「跑到第 5 步才发现锚点失效，而前 4 步已经点完了」——桌面动作不可逆，这是最贵的一类失败 |
| 我们采纳 | `orb/wfPreflight.mjs` + `action=preflight` + 面板「预检」按钮 |
| 落地形态 | **两层，等级刻意不同**：① 静态自洽（缺工具名 / 循环体空 / 子流程引用已删配方 / 编排图有环）判 `block`，**必然失败才劝停**；② 快照核对（锚点能否解析）只判 `warn` |
| 差异与理由 | 一次快照看不到中途状态（第 1 步才打开应用、第 3 步才点进那个页面），所以锚点问题判 `block` 会天天误报，误报几次这个功能就没人用了。**Visible/Stable/Receives Events 做不了**：windows-mcp 的快照不带 z-order、遮挡、动画帧信息，硬做只能编 |
| 诚实边界 | 只做「元素能否解析到」（≈ Playwright 的 attached）。录制坐标型步骤查不出"还是不是原来那个控件"，只能报"附近有/没有可点控件"，并明确标 `weak` / `unverifiable` |

### 1.2 重试要带抖动 — AWS Full Jitter

| 项 | 内容 |
|---|---|
| 一手来源 | AWS Architecture Blog《Exponential Backoff And Jitter》：`sleep = random(0, min(cap, base * 2^attempt))`，并明确结论"the no-jitter exponential backoff approach is the clear loser" |
| 它解决的问题 | 固定间隔会在**同一时刻**反复撞同一堵墙（界面还没重绘完、目标进程还没起来），退避等于没退 |
| 我们采纳 | `orb/autoRetry.mjs` 的 `backoffMs()` 默认 `jitter:"full"` |
| 差异与理由 | ① 加了 `floorMs = 50` 地板。AWS 允许退到 0 —— 云端请求 0 延迟重试无所谓，**桌面动作 0 延迟等于"立刻再点一次"**，那正是重试要避免的。② 保留 `jitter:"none"`：需要可复算的场合（日志核对、单测断言）得能算准，不留这个口子连"到底等了多久"都查不了 |
| 备注 | 桌面重试默认 `maxAttempts=2`，抖动带来的收益本来就有限；但"同一节奏硬撞"是唯一能让两次重试都白试的原因，去掉它几乎零成本 |

### 1.3 中断后接着跑 vs 代码变了 — Temporal determinism

| 项 | 内容 |
|---|---|
| 一手来源 | Temporal 文档 *Workflow determinism / replay testing*：非确定性错误来自「代码变更 + 还有在跑的历史」，重放会走岔 |
| 它解决的问题 | 原来 `canResume` 只比**步数**。步数一样但内容改过（改了坐标、换了锚点、调了等待）时，断点索引看着"对得上"，续跑却从错的位置接上 |
| 我们采纳 | `orb/wfCheckpoint.mjs` 增加 `recipeDigest()`（内容指纹），断点落盘时存 `stepsDigest`，续跑前逐字比对 |
| 落地形态 | 步数不符 → 拒；步数相同但指纹不符 → 拒；**旧断点没有指纹 → 也拒**（无从核对就不放行，宁可从头跑） |
| 差异与理由 | 不做完整重放测试（Temporal 那套要可重入的事件历史，桌面 GUI 没有事件溯源）。对桌面场景，"配方内容没变"就是确定性检查的全部所需 |
| 题外话 | 这条第一次做的时候就是漏的 —— 只比步数看着挺合理，直到有人改了第 5 步的坐标而步数没变。**对标的价值常常不在"学到新招"，而在"发现自己以为做对的地方是漏的"** |

### 1.4 失败了敢不敢重试 — 风险分级 + 幂等收据

| 项 | 内容 |
|---|---|
| 一手来源 | AWS Builders' Library（幂等键、重试与幂等的关系）；GitHub Actions 的 concurrency / 单飞 |
| 落地 | `orb/autoRetry.mjs`：三条放行条件缺一不重试（错误码属界面漂移族 + 动作可逆 + 未达上限）；`PERM_DENIED` 一律 hard-stop；不可逆动作直接判死，不看错误码 |
| 为什么不能"重试就好了" | 桌面和云端最大的区别：点过「提交」再点一次就是提交两次。云端重试靠幂等键兜住，桌面没有服务端幂等，只能在**动作层**判死 |

### 1.5 跑完凭什么说成功 — 三档结论 + 已结算收据

| 项 | 内容 |
|---|---|
| 一手来源 | n8n 的 "validation passing is necessary, not sufficient"（能跑通 ≠ 做成了） |
| 落地 | `ok / failed / needs_review` 三档；**拿不到证据默认 `needs_review`，绝不因"没报错"判成功**；收据 `settled` 是"这一步确实做成了"的独立痕迹 |
| 复核不改判 | `markReviewed` 只追加 `reviewedAt / reviewedBy / reviewVerdict / reviewNote`，**永不改写 status / verdict**。一旦用人的判断覆盖 verdict，`autoPolicy` 就把主观结论当零退化样本，绕回自证循环 |
| 取证而不猜 | `tree_state` 判据不给自动建议（猜错会"永远判失败"），改为列"上次运行后界面新出现哪些行"候选，**默认不勾** |

### 1.6 排障要看得到断在哪一步 — trace 与作用域

| 项 | 内容 |
|---|---|
| 一手来源 | Playwright Trace Viewer 的分步快照思路；UiPath Retry Scope 的作用域语义 |
| 落地 | `orb/autoTrace.mjs` 步级轨迹；子流程**共享父级 runId**，打 `nested:true` + `node` 标记，不自己 begin/end、不抢进度条、不继承 `resumeFrom` |
| 理由 | 不共享的话，父层只剩一句"子流程 X 失败"，而它自己的第几步挂了完全查不到；让子流程自己 begin 又会让进度条跳回 0，看着像重新开始了 |

### 1.7 删东西前先查引用 — 引用完整性

| 项 | 内容 |
|---|---|
| 一手来源 | n8n 四道门里的 **verify connections**：发布前校验引用完整 |
| 它解决的问题 | 删掉配方 B，引用它的 A 要到**运行时**才炸 —— 删的那一刻一切正常，报错在几天后的半夜 |
| 落地 | `subflowReferrersOf()`：删之前扫全部配方（含 `steps` 里的 `type:"subflow"` 与**编排图里的 `kind:"subflow"` 节点**，后者最容易漏）；命中则返回 `code:"referenced"` + 谁/在第几步；确认后 `force:true` 放行 |
| 为什么不用硬拒绝 | 两条一起删是合理需求。硬拒绝会把人卡死，逼他去改一条准备删掉的配方 |

### 1.8 明确**不适配**的：熔断器（Hystrix / Resilience4j）

| 项 | 内容 |
|---|---|
| 结论 | **不做** |
| 理由 | 熔断解决的是"下游持续故障时快速失败，别把线程池打满"。桌面场景是**GUI 独占 + 单用户 + 串行**：没有并发风暴可打满，也没有"半开状态探测"的意义——界面坏了就是坏了，多试一次只会多一次误点。对应场景由 `autoPolicy` 降级（执行 → 观察）兜底，比熔断更对症 |
| 记在这里的原因 | 不然下一个人看到"没有熔断"会以为是漏项，再花一周论证一遍 |

### 1.9 明确**不做**的其它几项

| 项 | 为什么不做 |
|---|---|
| OpenTelemetry 全量语义约定 | 账本字段已覆盖 runId / 步号 / 证据等级 / 原因码；再套一层 span 模型，收益是"能接 Grafana"，成本是把单机账本改造成分布式追踪 —— 现阶段没人消费这些数据 |
| 分布式锁 / 选主 | 单机单实例，`guiLock` + 幂等收据已经够；引入选主只会多一个能挂的组件 |
| 拖拽式 DAG 画布 | 真实配置动作只有三件：加节点、选类型、指依赖。拖拽要处理布局、缩放、连线命中、撤销栈，上千行换一个"看起来高级"的入口。**列表式编辑器**（`openWfGraph`）能做完这三件事，还天然可键盘操作、可被静态检查扫到 |

## 4. 还差的（诚实清单）

1. **预检只做静态与"能不能解析"**。真跑一次（n8n 的 test 门）仍然是判断"这条配方到底行不行"的唯一硬证据 —— 预检只能把明显会坏的提前挑出来。
2. **内容指纹是 32 位 FNV**。对"配方改没改"够用（不是安全用途），理论上存在碰撞。要更强就换成按步哈希链，本轮没做。
3. **熔断/限流不做**，理由见 1.8。若将来引入多实例或多任务并发，这一条要重新评估。
4. **`cache/` 与 `ORB存储/` 同名目录并存**（中间态 vs 成品）。已写进 `SRC-INDEX.md` 说明，不做合并 —— 合并要动 100+ 处路径引用，收益只是"看起来整齐"。
