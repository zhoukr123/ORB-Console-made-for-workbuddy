# 代码签名三条路线：工程量与可行性评估

> 评估日期：2026-10-22
> 对象：ORB 控制台 v1.0.1（Electron 44 + 自研自解压单文件，208 MB，MIT，GitHub Release 分发）
> 前置状态：**桩已完成签名感知改造**（`docs/代码签名获取方案调研.md` §8.6），三条路线都不需要再动 `orb-sfx.c`
> 本文只回答两件事：**要改多少东西**、**改完能不能成**

---

## 0. 三条路线其实不是同一类问题

| 路线 | 它解决的其实是 | 真正的工作量在哪 |
| --- | --- | --- |
| A. Certum 证书 | **证书**（你是谁） | 几乎为零，工作量在"申请材料 + 等审核" |
| B. SignPath Foundation | **证书 + 构建可溯源** | 在你的 CI 上（本地手工打包不能签） |
| C. Microsoft Store / MSIX | **分发形态**（证书顺手解决） | 在应用架构上（自解压、数据目录、卸载全部要改） |

**所以 C 比 B 贵一个数量级，不是因为它更"高级"，而是因为它要求你把程序改成"受管包"。**

---

## 1. 基线：三条路线共同面对的现状（均已核对代码）

| 事实 | 位置 | 影响哪条路线 |
| --- | --- | --- |
| 发布物 = `[桩 142,336 B][payload zip ~165 MB][32 B trailer]` 单文件，本地 `node orb/pack.cjs` 生成 | `orb/pack.cjs:326-397` | B（必须搬进 CI）、C（这套链路整体作废） |
| `pack.cjs` 有 4 个硬校验：4 个原生 exe、`orb/node_modules`、`orb/runtime/python`（含 `LICENSE.txt`）、桥的相对导入审计 | `orb/pack.cjs:150-240` | B（CI 上要全部复现） |
| 程序**自解压到 `%LOCALAPPDATA%\ORBConsole`** 再跑 `启动 ORB 控制台.cmd` | `orb-sfx.c` §运行流程 | C（MSIX 只读安装目录，这套必须废弃） |
| 用户数据在 `%APPDATA%\ORB 控制台` | `main.js:34` | C（MSIX 会重定向，老用户数据"消失"） |
| ASR 权重写入**包内** `asr/models`（首次点安装才下，~483 MB） | `pack.cjs` ASR 段 + `asr/prepare.ps1` | C（包内只读 → 必须改路径） |
| 桥监听 `127.0.0.1:19387`，面板 CSP 只放行这一个地址 | `main.js:116, 3012` | C（打包应用回环行为需实测） |
| 会 `spawn("powershell.exe", -EncodedCommand ...)`、拉起 3 个原生 exe、拉起 node 桥进程 | `main.js:1104, 1077, 1418, 1909` | C（审核关注点）、B（SignPath "no hacking tools" 条款自查） |
| 卸载靠 `.cmd` 自我搬迁 + `taskkill` 专名进程 + 删目录 | `卸载 ORB 控制台.cmd` | C（MSIX 不需要也不允许） |
| `.github/workflows/release.yml` 已存在，但**作者自己标注"尚未在任何 CI runner 上真实跑通"** | `release.yml:1-20` | B（这是全部工作量的核心） |
| GitHub Star = 0，仓库建于 2026-10-15 | `gh api` 查于 2026-10-22 | A1（免费通道的硬门槛） |

## 2. 路线 A：Certum 开源证书

### A1. 免费通道 —— 工程量几乎为零，但门槛不由你决定

| 项 | 内容 |
| --- | --- |
| 条件 | GitHub 托管 + **Star > 1000** + 至少一个 Release + 申请人中国国籍 |
| 本项目 | 国籍 ✓ / Release ✓ / **Star = 0** ❌ |
| 工程量 | 0.5 人日（证书到手后接进发版流程，`orb/sign.cjs` 已就绪） |
| **可行性** | ❌ **短期不可行**。这不是工程问题，是社区增长问题，不可控、不可排期 |

> 定位：**期权，不是计划**。Star 破千之前不要把它写进任何路线图。

### A2. 付费版 —— 目前唯一"花钱就能立刻确定"的路

| 项 | 内容 |
| --- | --- |
| 价格 | €49/年 ≈ ¥374（云 HSM 版，无 USB 令牌） |
| 申请 | 身份证 + 地址证明 + GitHub 仓库链接，1–5 个工作日 |
| 工程量 | **0.5 人日**：① 在 `pack.cjs` 末尾调一次 `sign.cjs`；② 发版清单加一步；③ 首次验证签后便携包能解压 |
| 已有基建 | `orb/sign.cjs` 全部就绪（自动挑 signtool、RFC 3161 时间戳、旧桩拒签、签后 trailer 回归） |
| 主要风险 | ① **经常缺货**（第三方记录：2026-09 长期 out of stock）；② SimplySign 客户端要常驻才能签（云 HSM 的代价）；③ 发布者显示你的真实姓名（对个人项目是加分，对商业项目要斟酌） |
| **可行性** | ✅ **高**。唯一不确定的是库存和审核速度，技术侧零风险 |

## 3. 路线 B：SignPath Foundation（免费，但要先有可溯源 CI）

### 3.1 资格对照

| SignPath 条件 | 本项目 | 判定 |
| --- | --- | --- |
| OSI 认可的开源许可 | MIT | ✅ |
| 公开仓库、活跃维护 | 是 | ✅ |
| 已有 Release | v1.0.0 / v1.0.1 | ✅ |
| 不含专有代码 | 未随包分发 CodeBuddy CLI；Electron/Node/Python 均为 OSS | ✅ |
| **二进制可溯源到仓库的自动构建** | `release.yml` **从未跑通**，发版一直手工 `pack.cjs` | ❌ **核心工作量在这** |
| 每次发布人工审批 | 单人项目可接受 | ✅ |
| 团队全员 MFA + 三角色（author/reviewer/approver） | 单人可兼任，但必须开 MFA | ⚠️ 需配置 |
| 主页公示 code signing policy | 没有 | ❌ 待补 |
| 不含识别/利用漏洞、绕过执行环境安全措施的功能 | 键鼠模拟、截图、前台探测、执行任意 PowerShell | ⚠️ **裁量风险** |
| 发布者身份 | **SignPath Foundation**（不是你） | ⚠️ 品牌让渡 |

### 3.2 工程量分解

| # | 任务 | 人日 | 说明 |
| --- | --- | --- | --- |
| 1 | 让 `release.yml` 在 windows-latest 上跑通 | **2–3** | 未知数集中在：MSVC 四件套能否编过、`build-runtime.ps1` 拉 embeddable CPython + pip 装依赖、165 MB zip 的耗时、`C:/Windows/System32/tar.exe` 是否存在（runner 上有） |
| 2 | 接入 SignPath GitHub Action（上传 → 签名 → 取回） | 0.5 | 官方 action 结构清晰；把 `sign.cjs` 的边界交给它 |
| 3 | 补政策文件：`CODE_SIGNING_POLICY.md`、隐私政策、角色说明、README 入口 | 0.5–1 | 纯文档 |
| 4 | 首个签名版本端到端验证（签后单文件能解压能启动） | 0.5 | 桩已就绪，这步现在很快 |
| | **合计** | **3.5–5 人日** | 不含对方审核的 1–3 周（人工等待，不占你的工时） |

### 3.3 这条路真正改变的是什么

- **发版方式被迫迁移**：签名版只能由 CI 产出。本地 `node orb/pack.cjs` 出来的包签不了（不可溯源）。
  这意味着"打包前必须确认 worker 停笔"这类本地纪律，要换成"提交 → CI 构建 → 审批 → 签名"。
- **每次发版多一道人工审批**：SignPath 的审批是人工的，急发补丁会被这一步卡住。
- **发布者变成 SignPath Foundation**：用户看到的 UAC 发布者是基金会，不是"ORB 控制台"。

### 3.4 可行性判定

**⚠️ 中等。** 唯一可能被拒的是"自动化他人应用 / 执行任意命令"这条裁量项 —— 申请时要把用途写清楚
（本机效率工具、用户显式授权、不涉及漏洞利用），但基金会保留不解释拒绝的权利。
**技术侧没有不可逾越的障碍**。

> 有两点需要向 SignPath 问清（我无法替你确认）：① 208 MB 单文件的体积/时长上限；
> ② 单人项目如何满足"reviewer 与 author 分离"的角色要求。

## 4. 路线 C：Microsoft Store / MSIX（唯一零警告，代价最大）

### 4.1 它不是"签名方案"，是"重做分发"

MSIX 要求应用**安装到只读的 `C:\Program Files\WindowsApps` 原地运行**。本项目的三条命脉 ——
自解压、可写数据目录、`.cmd` 卸载器 —— 全部与该模型冲突。

| 现状 | MSIX 下会怎样 | 改动量 |
| --- | --- | --- |
| 单文件自解压 → `%LOCALAPPDATA%\ORBConsole` → 跑 `.cmd` 启动 | 不允许：安装目录只读，也不能"解压自己再运行" | **大**：整个 sfx 链路（桩/trailer/pack 拼装）作废，改由 electron-builder 出 appx；`启动 ORB 控制台.cmd`、`ORB 控制台.exe` 重命名逻辑全部重做 |
| `DATA_DIR = %APPDATA%\ORB 控制台` | 打包应用的 `%APPDATA%` 会被<strong>虚拟化重定向</strong>到 `%LOCALAPPDATA%\Packages\<PFN>\LocalCache\Roaming` | 中：老用户升级后"数据不见"；要申请 `unvirtualizedResources`（需商店单独批准）或写迁移逻辑 |
| ASR 权重下到包内 `asr/models`（483 MB） | **包内只读 → 直接失败** | 中：`asr/prepare.ps1` 与 `bridge.mjs` 的路径解析全改成 `userData` |
| 桥监听 `127.0.0.1:19387` | 全信任打包应用通常可用，但打包应用的回环/防火墙行为与未打包不同 | 小–中：**需实测**，不能照抄 |
| `spawn powershell.exe -EncodedCommand`、拉起原生 exe | 技术上允许（全信任），但这是**审核重点**：应用等于"能执行任意系统命令" | 大（审核侧）：需要在提交说明里解释，仍有被拒风险 |
| `.cmd` 卸载器 taskkill + 删目录 | 不需要、也不允许 | 小：删除即可 |
| 分发形态 | 只能走 Store（或旁加载，但旁加载又要证书，等于回到问题起点） | **结构性**：从"下载一个 exe"变成"去商店装" |

### 4.2 工程量分解

| # | 任务 | 人日 |
| --- | --- | --- |
| 1 | Partner Center 个人账号 + 预约应用名，拿到 Identity Name / Publisher CN | 0.5（验证另需 1–5 天） |
| 2 | 打通 electron-builder 的 `appx` 目标（图标资产、publisherName 对齐、asar:false 下的资源布局） | 2–3 |
| 3 | 数据目录适配（虚拟化 or `unvirtualizedResources` + 迁移） | 1–2 |
| 4 | ASR 权重路径改造（包内 → userData），含旧数据迁移 | 1–2 |
| 5 | 回环/端口/防火墙在打包态实测与修正 | 1–2 |
| 6 | 清理卸载器、启动器、sfx 相关分支 | 1 |
| 7 | 商店素材：截图、隐私政策、年龄分级、10.8 相关声明 | 1–2 |
| 8 | 提交与返工（经验值 1–3 轮，每轮 3–10 天） | 1–3 |
| | **合计** | **8–15 人日 + 3–6 周日历时间** |
| | **长期** | 双轨维护：便携版（现有用户）与商店版（新用户）两套产物、两套路径分支 |

### 4.3 可行性判定

**⚠️ 低–中。**

- **技术上**：Electron 打 MSIX 是成熟路径（electron-builder 原生支持），不是科研项目。
- **政策上**：风险集中在两点 ——
  ① "应用能执行任意 PowerShell / 自动化其他程序"在审核里属于高危特征；
  ② 首次运行下载 483 MB 模型权重，容易被判为"安装额外软件"（政策 10.8）。
- **战略上**：走通之后你要长期维护两条产物线，且现有"双击即用单文件"的卖点对商店用户消失。

> **建议先做 1–2 人日的 PoC**：只验证"能不能把当前 app 打成 appx、在本机旁加载跑起来、桥能起、ASR 能跑"。
> PoC 不通过就不要投后面那 10 人日。

## 5. 横向对比

| | A1 Certum 免费 | A2 Certum 付费 | B SignPath | C MS Store / MSIX |
| --- | --- | --- | --- | --- |
| 直接成本 | ¥0 | **¥374/年** | ¥0 | ¥0 |
| 工程量 | 0.5 人日 | **0.5 人日** | 3.5–5 人日 | 8–15 人日 + 长期双轨 |
| 拿到签名包 | 不可预期（等 Star） | **1–5 个工作日** | 2–4 周（含审核） | 3–6 周（含审核与返工） |
| UAC 发布者显示 | 你的姓名 | **你的姓名** | SignPath Foundation | 你的开发者名 |
| 首次安装是否被拦 | 有 SmartScreen，无"未知发布者" | 同左 | 同左 | **零警告** |
| 发版方式 | 不变（本地打包） | 不变 | **必须走 CI + 人工审批** | 走 Store 提交 |
| 主要风险 | Star 涨不上去 | 缺货、云 HSM 客户端常驻 | 裁量拒签、条款自查 | 政策审核、架构冲突、沉没成本 |
| **可行性** | ❌ 不可排期 | ✅ **高** | ⚠️ 中 | ⚠️ 低–中 |

**三条路线的共同点**（必须先接受）：除 Store 外，**没有任何证书能立刻消除 SmartScreen 警告**。
签名只是让"未知发布者"变成"你的名字"，警告本身要靠数周 + 数百次干净安装的声誉累积才会退。

## 6. 决策建议

```
能不能接受"用户看到的发布者是 SignPath Foundation"？
├─ 能 ──→ 走 B。顺便把 release.yml 修好，长期收益远超签名本身
└─ 不能
   ├─ 现在就要能签 ──→ 走 A2（¥374），0.5 人日，本周完成
   └─ 只接受"零警告" ──→ 先做 C 的 1–2 天 PoC，通过再投 8–15 人日
```

**不建议做的事**：

| 做法 | 为什么不做 |
| --- | --- |
| 等 Star 涨到 1000 走 A1 | 不可控、不可排期。Star 是运营结果，不是工程任务 |
| 自签名 + 让用户导入根证书 | 等于让用户信任一个能签任意程序的 CA，杀软报毒、用户拒绝，比不签名更差 |
| 自签名给自己"先有个签名" | 除了本机自测没有任何收益，还会污染签名记录 |
| 同时铺 B 和 C | 一个要改 CI、一个要改架构，双线并行会互相拖慢，先做 PoC 再决定 |
